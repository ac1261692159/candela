# PRD：单用户行为序列（某用户在指定时间段的全部上报事件）

> phase: `clklog-analytics-user-timeline-v1`
> 状态：**已评审定稿（决议见 §0/§5），实施中**
> 对标：数数（ThinkingData）「用户 → 用户详情 → 行为序列」
> 相关既有能力：Debug 实时查询（接入验证，100 行上限 / 固定窗口）、事件分析「用户数」下钻（只能存分群）、用户分群 / 用户标签 / 分析主体

---

## 0. 归属建议：放 **用户模块**（推荐），不放分析模块

| 维度 | 用户模块（推荐） | 分析模块（备选） |
|---|---|---|
| 输入主键 | **用户**（主体 + 用户标识）——与分群/标签/主体同族 | 事件 + 指标（按事件聚合） |
| 输出形态 | 单人明细流（行为序列） | 聚合结果 + 图表 |
| 行业惯例 | （**已纠错 2026-10-08**）数数把「行为序列」放在**分析**组、紧接「用户列表」；「用户」组下是标签/分群/用户细查 | 数数的分析模块含事件/漏斗/留存/路径等聚合模型，行为序列也在这一组 |
| 交互入口 | 未来可从「分群成员 / 标签成员」下钻到某个人的行为序列（用户模块内部闭环） | 需跨模块跳转 |
| 与现有菜单的关系 | 用户菜单现有三项是**可保存资产**（分群/标签/主体），本功能是**即席查询**，形态略不同 | 分析菜单现有三项都是即席查询，形态一致 |

**结论（已定）**：放用户模块。标签用「用户行为序列」（英文 `User timeline`）。
路径沿用用户菜单既有约定（`/analysis/cohorts`、`/analysis/tags`、`/analysis/subjects` 都在 `/analysis/` 前缀下）：
**`/analysis/user-timeline`**，并支持深链 `?subject=<id>&value=<用户标识>&from=&to=`（便于分享/收藏某个人的行为回溯）。

> ⚠️ **2026-10-08 纠错**：本条建议的「行业惯例」依据写错了——数数把行为序列放在**分析**组（`code=user_streams`），
> 不在「用户」下。详见 `docs/product/research-clklog-analytics-user-timeline-vs-thinkingdata.md` §2.1/§4.1；
> 「归属」这条重新开放，等评审在新证据下再定（移动成本 = 菜单 1 行 + 路由不变）。

## 1. 背景与问题

- 分析师拿到一个用户标识（设备 ID / 账号 ID），想看**这个人这段时间到底做了什么**（按时间先后看事件流），
  目前只有两条弯路：
  1. **Debug 实时查询**：定位是埋点接入验证，最多 100 行、窗口只有 1h/24h/7d 三档、不能选任意起止时间；
  2. **事件分析**：结果是聚合值；点「用户数」只能把该单元格的用户**存成分群**，看不到单个人的事件明细。
- 数数（对标产品）的「用户行为序列」正是这个缺口：给定用户 + 时间段，按序列出该用户全部上报事件，用于
  行为分析、客诉定位、埋点异常排查。

## 2. 阶段目标与范围

**做**：

1. 新页面「用户行为序列」：按**分析主体 + 用户标识 + 起止时间**（可到分钟）查询单个用户的全部上报事件；
2. 结果包含**汇总**（事件总数、事件种类数、时间跨度、首/末事件时间）与**事件流表格**（时间 / 事件 / 关键属性，可展开全部 properties）；
3. 支持**事件名多选过滤**（可选条件，且能显著加速）、**时间正序/倒序**切换、**每条页数**选择；
4. 复用 Debug 已上线的**两段式异步**（快查询秒回；长区间转后台，完成后就地渲染）；
5. 复用**查询记录**能力：每次查询留一条记录，可回看（沿用「留档」语义与项目开关）。

**不做（非目标）**：

- 不做会话切分、路径图、序列模式挖掘（本期只给「事件流 + 汇总」）；
- 不做属性条件筛选（只做事件名多选；属性筛选留后续）；
- 不做导出（xlsx/csv 留后续）；
- 不做「全部历史无上限」——单次结果有上限（见 R5），超出如实标注；
- 不改 Debug 页与事件分析页的既有行为（只新增入口，可后续把「分群成员 → 行为序列」接上）。

## 3. 需求

- **R1 主体与标识**：用平台的**分析主体**机制选主体（预置「用户」= `if(user_key != '', user_key, distinct_id)`；也支持属性主体），
  输入一个用户标识值；**不做**「distinct_id / user_key 二选一」的自造语义（主体机制已覆盖）。
- **R2 时间范围**：起止时间可选到分钟，默认「最近 7 天」（区间越短越快）；范围上限（如 92 天）与提示见 R6。
- **R3 事件多选**：可选；选中后结果只含这些事件，且**查询更快**（事件名是 `sa_events` 排序键首列），
  界面按 Debug 的既有做法给出「选事件名会快很多」的提示。
- **R4 结果**：
  - 汇总条：事件总数（命中总数）、已显示条数、事件种类数、时间跨度；
  - 表格：时间（按平台时区墙钟渲染，与 Debug 同一口径）、事件（显示名 + 原始事件名）、关键属性预览，展开行看完整 properties；
  - 排序：默认**时间正序**（序列语义），可切倒序。
- **R5 上限与截断**：单次最多物化 **5000 行**；超出时如实标注「仅显示前 N 条（命中 M 条）」，不静默截断。
- **R6 性能与异步**：8 秒预算内同步返回；超预算转后台执行、完成后就地渲染（复用已验证的两段式）。
  时间范围 > 7 天时在提交前给出「可能较慢」的提示。
- **R7 查询记录**：每次查询留一条记录（条件 + 命中数 + 结果快照 + 状态 + 操作人），可在页面内回看；
  项目关闭「留档」时不留痕（与 Debug 同口径：超预算查询此时不转后台，如实报超时）。
- **R8 权限（已定决议）**：本功能**单独开权限码** `timeline.view`，授予**数据分析师（analyst）/ 分析管理员（analysis_admin）/ 超管（super_admin）**，
  **按项目隔离**（非本项目成员看不到）；超管由平台角色自动全权（`iam-evaluate` 既有规则）。
  说明：`project_owner` 一并纳入（权限目录里同类码 owner 恒为 true，且 owner 是项目内权限最高者）——如要严格按三人清单排除 owner，改一行即可。
- **R9 多语言**：新增文案**全部走 i18n**，13 种语言一次补齐；用户数据（事件名、属性名、标识值、用户自建显示名）不翻译。

## 4. 验收标准

| 编号 | 判据 |
|---|---|
| UT-1 | 给定主体 + 标识 + 起止时间，结果与该用户在该区间的 `sa_events` 原始行**逐行一致**（直查对拍） |
| UT-2 | 汇总四项正确（总数 = `count()`、种类数、时间跨度、首末时间） |
| UT-3 | 时间列显示与 Debug 同口径（平台时区墙钟，不偏时区）；排序切换生效 |
| UT-4 | 事件多选过滤后结果只含所选事件，且耗时/读行数明显下降（给出实测数字） |
| UT-5 | 长区间（如 30 天）超预算 → 转后台并在完成后就地渲染；期间页面可继续操作 |
| UT-6 | 超过 5000 行时如实标注截断（显示条数、命中条数），`meta` 里 `truncated=true` |
| UT-7 | 查询记录可回看；项目关闭留档时不留痕（超预算如实报超时） |
| UT-8 | 权限：无 `meta.view` 的角色访问接口 403；跨项目不可见 |
| UT-9 | 13 语言键集/占位符一致（`i18n_check`），无硬编码文案（`i18n_scan --check` 持平） |
| UT-10 | 门禁全绿（后端/前端构建与单测、`arch_ratchet`） |

## 5. 风险与开放问题

| 编号 | 事项 | 建议 |
|---|---|---|
| O-1 | **归属**（用户模块 vs 分析模块） | **已定：用户模块**（见 §0） |
| O-2 | **明细页是否套用行级数据策略**（`SaDataPolicy` 的 row_filter / 事件范围） | **已定：同口径** —— 与 Debug 一致（不套用行级数据策略，仅功能权限 + 项目隔离）；「明细类页面是否套用数据策略」另立议题统一决策 |
| O-3 | 查看单用户全量事件属敏感数据（可看到某个人的完整行为） | 与 Debug 同级别的数据；已具备项目隔离 + 权限门禁。建议后续加「访问审计」（谁在什么时候查了哪个用户） |
| O-4 | 5000 行够不够 | 极端活跃用户 7 天可达 1.5 万+ 事件（本平台实测样本）；v1 截断并标注，后续可做「按时间分段加载」 |
| O-5 | 与 Debug 的边界 | Debug = 接入验证（窗口固定、100 行）；行为序列 = 行为分析（任意区间、5000 行、有汇总）。两者入口分属「数据管理」与「用户」，文档里互相指路 |

## 7. v2 改版：主界面重做（`phase: clklog-analytics-user-timeline-ux-v1`，已批准 2026-10-08）

**背景**：用户反馈「这长得太像 Debug 了」；调研数数「行为序列」后（`docs/product/research-clklog-analytics-user-timeline-vs-thinkingdata.md`）确认：
v1 第一屏是「查询表单 + 原始事件表」，与 Debug 同形；数数第一屏是「**这个人是谁 + 他这段时间怎么样**」，明细在第三层。

**目标与范围（本 phase 做）**：

1. **三段式主界面**：左栏＝用户画像（用户属性 + 标签最新值）+ 概览数字；右栏＝行为概览（每日事件量趋势 + 事件占比饼图）→ 外显属性 → 行为明细；
2. **概览先行**：概览只做聚合（不读 properties），**即使明细转后台也先返回**，页面立刻有内容；
3. **外显属性**：把选定的属性直接渲染为明细列（不必逐行展开 properties）；选择记忆在本地；
4. **切换用户**：支持一次带入多个用户标识（手填多行 / 从用户分群成员带入），页内「上一个 / 下一个」按序查看；
5. **去 Debug 化**：查询记录收进**抽屉**（不再占主界面一块）；主界面标题/说明改为行为分析口径。

**非目标**：归属不动（用户模块，用户已定，不随数数挪到分析）；不做「查看前后行为」与明细内属性筛选（P2，登记后续）；
不做会话切分/会话回放/路径图；不改权限与留档口径（`timeline.view` + 项目隔离 + 同口径）。

**验收（UT2-1~UT2-6）**：

| 编号 | 判据 |
|---|---|
| UT2-1 | 主界面不再出现「表单 + 原始表」两段式；左栏有用户属性、右栏有趋势图与占比图（截图佐证） |
| UT2-2 | 概览先行：明细超预算转后台时，趋势/占比/汇总**已经渲染**（不需要等后台任务） |
| UT2-3 | 外显属性：勾选 2 个属性后，明细表出现对应两列，值与 properties 原文一致；刷新后选择仍保留 |
| UT2-4 | 切换用户：带入 3 个标识后可「下一个」循环，且每次切换都会刷新画像与概览 |
| UT2-5 | 记录区在抽屉里（主界面无记录表），抽屉内状态列/查看/删除与 v1 一致 |
| UT2-6 | 门禁全绿；新增文案 13 语言齐备（含图表标题/图例/空态） |
## 8. v3：使用者只知业务属性怎么办（`phase: clklog-analytics-user-timeline-ux-v1` 增量，2026-10-08）

### 8.1 需求（来自真实使用者反馈）

> 「我作为使用者并不知道用户标识是什么，我只知道你给了我这个 `1_14552557`——这对应着什么属性？
> 如果使用者只想用指定的用户属性如 `massid` 为 `YYZ000014552557` 进行查询，我们的平台做不到。」

两条要求：

1. **能按业务属性查**：输入 `massid = YYZ000014552557` 就能查到这个人（不需要知道 `1_14552557`）。
2. **平台负责翻译**：查询后要告诉使用者「这个名字对应平台里的哪个用户标识」，让属性与内部标识建立可见联系。

### 8.2 需求细化

| 编号 | 需求 | 说明 |
|---|---|---|
| T-1 | 标识类型可选 | 查询条上给「标识类型」：**用户标识**（默认）/ **用户属性** |
| T-2 | 属性键从字典选 | 选「用户属性」后出现属性键下拉（取自用户属性字典，如 `massid`），值手填 |
| T-3 | 文案解释清楚各自含义 | 用户标识 = 内部 ID（`user_key` 优先，否则 `distinct_id`，形如 `1_14552557`）；用户属性 = 直接填业务属性值，无需知道内部 ID |
| T-4 | **回显解析结果** | 查询后显示「已解析为用户标识 `1_14552557`」；匹配到多个标识时显示个数并合并展示 |
| T-5 | 查不到要说清楚 | 属性键或值不对 → 明确提示「未找到该属性值对应的用户：`massid` = `YYZ…`」，不返回空表明说「这个人没有行为」 |
| T-6 | 多语言 | 以上文案全部 13 语言齐备 |

### 8.3 验收标准

| 编号 | 判据 |
|---|---|
| UT3-1 | 同一区间的同一人：按 `distinct_id` 查与按 `massid` 查**命中数、事件种类、首末时间完全一致**（生产实测） |
| UT3-2 | 页面显示「已解析为用户标识 …」，且值与该人的 `distinct_id` 一致 |
| UT3-3 | 属性值不存在 → 400 + 本地化提示（不是空表，也不是 500） |
| UT3-4 | 用户属性既能作为**查询标识**，也能作为**服务端筛选**（`filter_scope=user`） |
| UT3-5 | 任何用户属性条件都**不产生对事件表的 JOIN**（单测钉住 SQL 形状；见设计 §11 红线） |
| UT3-6 | 门禁全绿；新增 3 键 × 13 语言 |

### 8.4 非目标

- 不做「属性值 → 用户列表」的反查页面（批量找人走用户分群）。
- 不支持模糊匹配 / 多值匹配（`LIKE`、`IN`）：等值是唯一语义，避免误伤。
- 不引入新的分析主体类型：属性查仍走「默认用户主体」的行级表达式，口径与按标识查一致。
