# 对拍口径白皮书：1.2% 日总量差与事件级差异的归因

> phase: `clklog-data-quality-ops-v1`（R3-a）。数据来源：**生产 17685/17686 部署代码实跑**的自动对拍
> （2026-10-08 单日，报告 `/data/logs/production/clklog_manager/reconcile/reconcile-auto-2026-10-08T17-46-12.txt`）
> 与 2026-10-08 的调研（`docs/product/research-clklog-data-quality-ops-v1.md`）。
> 本文给出**结论 + 证据 + 仍未定的问题**；不确定的地方不写成结论。

## 1. 结论摘要

| 结论 | 证据 |
|---|---|
| 日总量差 **+1.22%**（sa 多于 raw），且**高度集中**：Top 20 事件级差异合计 +404,317 行，占总量差 433,172 行的 **93.3%** | 报告 `daily` 行与 `event_diffs` 段 |
| 差异**单向**：本次 Top 20 差异全部为正（sa > raw），没有一条是 sa 少记 | 同上（正差 +404,317 / 负差 0） |
| **不是重复写**：sa 侧 CRC 近似重复 19,462 行 = **0.054%**，远低于 0.5% 容忍带 | 报告 `crc` 段 |
| **不是空 event 口径**：两侧已对称过滤（`event != ''`，R1 起），差异与它无关 | 对拍 SQL 契约（设计 §4.1） |
| 差异集中在 **Android SDK 的网络/系统类事件**，且个别事件的相对偏差极大 | `base_network_socket_reconnect_start` +66,451（+36.85%）、`base_network_socket_reconnect_error` +51,395（+231.97%）、`android_start_get_gateway` +26,799（+60.12%）、`base_performance_httprequest_report` +61,856（+0.42%，量大所以绝对差大） |

**一句话**：这不是「丢数」信号，而是**两侧口径不同**——我们的旁路 ingestor 保留的 Android 网络/系统类事件，
社区版链路没有等价计入。R3-b 的双向抽样进一步给出方向与机制（§4）：**社区版侧少，不是我们多**。

0.4%~0.5% 的相对差更像是两条链路（Flink 与我们的 ingestor）在同一主题上前置过滤/时间边界处理的差别。

## 3. 已排除的解释

| 解释 | 排除依据 |
|---|---|
| 空 event 行只在一侧被统计（R1 前的口径不对称） | R1 起两侧同样 `AND event != ''`；本报告即新口径产物 |
| raw 侧走 `toDate(log_time)` 导致跨日归属不同 | R1 起 raw 侧改用表自带 `stat_date`（与 sa 侧同口径），且实测两列值一致 |
| 我方重复写入 | CRC 近似重复 0.054%（容忍 0.5%），量级不足以解释 1.22% |
| 分区剪枝/时间下界把数据滤掉 | 对拍 SQL 只按 `stat_date` 范围过滤，两侧同界；抽样日两表分区数正常 |
| 对拍把已清理区间算成差异 | 本日 `skipped_days=0`、`out_of_retention_days=0` |

## 4. R3-b 双向抽样结论（原「未定项」已定）

工具：`scripts/reconcile.sh --type=detail --side=sa|raw`（抽样后按**秒级**伪键
`distinct_id + event + toDateTime(log_time)` 回查对侧；秒级是硬要求——sa 侧是 `DateTime64(3)`、
raw 侧是 `DateTime`，字符串直比永远不命中，R3-b 实施中踩到并修掉）。

| 抽样 | 命中率 | 结论 |
|---|---|---|
| sa→raw（我方 200 条，全事件） | **99.50%** | 我方几乎全部能在社区版找到对照 → 不是「我方凭空多写」 |
| raw→sa（社区版 200 条，全事件） | **100.00%** | 社区版抽样行 100% 存在于我方 → **我方没有漏记** |
| sa→raw（`base_network_socket_reconnect_start`，60 条） | 66.67% | 该事件我方有约 1/3 的行在社区版找不到对照 |

键结构对照（2026-10-08，按事件看「行数 / 用户×秒键数 / 每键行数」）：

| 事件 | sa 行数 | sa 键数 | sa 行/键 | raw 行数 | raw 键数 | raw 行/键 |
|---|---|---|---|---|---|---|
| `base_performance_httprequest_report` | 千万级 | 百万级 | 2.032 | 千万级 | 百万级 | 2.030 |
| `base_performance_resource_download_fail` | 333,375 | 169,497 | 1.967 | 321,318 | 165,876 | 1.937 |
| `base_network_socket_reconnect_start` | 249,662 | 168,671 | 1.480 | 180,334 | 123,214 | 1.464 |
| `android_gateway_error` | 33,144 | 11,618 | 2.853 | 5,511 | 2,053 | 2.684 |
| `android_start_get_gateway` | 73,183 | 51,568 | 1.419 | 44,586 | 41,070 | 1.086 |

**机制结论**：
1. 常规大流量事件两侧几乎完全一致（`httprequest` 的键数差 **+0.35%**、每键行数差 0.1%）——两条链路对多数事件等价；
2. 差异**不在「每键行数」**（两侧都保留同一用户同一秒的多行，比例接近），而在**「用户×秒键数」**：
   错误/重试类事件我方键数是社区版的 **1.3~5.7 倍**；
3. 结合「raw 抽样 100% 存在于我方」，可判定：**社区版链路对这类事件发生了抑制/丢弃，我方保留更完整**；
   因此 +1.2%~+1.6% 的日差属于**社区版侧少计**，不是我方多写、也不是我方丢数。
4. 仍属开放项（不影响上述判定）：社区版在哪一层抑制（receiver 限流 / Flink 过滤 / 会话折叠）——需要
   在社区版容器侧取日志或对同一 SDK 请求做端到端跟踪，超出本平台旁路可观测范围。

## 5. 阈值（已按本文建议落地）

- 原阈值 **10%**（历史遗留），实测日差 **1.2%~1.6%** → 长期不告警，等于没有告警。
- 2026-10-09 **已通过页面「对拍设置」改为 3%**（`ops_reconcile_config.threshold_pct=3`，
  审计 `reconcile_config_update`，操作人 admin）：3% 能抓住「某事件类型整体消失/翻倍」级别故障，
  又不被 1.2%~1.6% 的结构性差异淹没。**不降到 1% 以下**：那会天天告警，反而淹没真信号。
- 结构性事件（reconnect 系列）**暂不加入忽略清单**：靠事件级差异表（快照已存 Top 20）暴露其变化趋势；
  若后续确认社区版抑制属预期行为，再决定忽略或改为「按事件看趋势」而不是并进日总量。

## 6. 给使用者的操作建议

1. 看「数据质量」页时，先看**事件级差异 Top**：若差异集中在新出现的事件类型，通常是 SDK 新版本或链路变更，
   而不是丢数。
2. 「按日总量」偏差在 ±3% 内、且事件级差异条目稳定 → 属已知口径差，不必处理。
3. 若偏差**转负**（sa 少于 raw）或某事件计数**归零**，才优先怀疑 ingestor（消费停滞/写入失败）。
