# PRD：告警通知通道扩展（多通道 + 平台化配置）

- `phase: clklog-analytics-alert-channels-v1`
- 帽子：产品
- 上游：`docs/product/research-clklog-analytics-alert-channels-v1.md`（调研结论）、`prd-clklog-analytics-alerting-v4.md`（模板与通道现状）
- 触发：用户要求告警从「只接飞书」扩到钉钉/企业微信/邮件（平台可配发信邮箱）/短信（阿里云、腾讯云、AWS 等）/Telegram/WhatsApp；并明确本项目**要开源、要覆盖海外**、尽量复用现成方案

---

## 1. 阶段目标与范围（门禁要素①）

把告警通道从 3 个（飞书 / SMTP / 腾讯云短信）扩到**一组可配置通道**，并让使用者在平台界面里自配凭证与接收人——开源分发不能预置任何厂商凭证。

**本期交付（P1 + P2 + P3 骨架）**

| 组 | 通道 | 说明 |
|---|---|---|
| 通用 | **通用 Webhook**（自定义 URL / headers / body 模板） | 长尾渠道零代码接入（PagerDuty / Opsgenie / Grafana OnCall / 自建系统…） |
| 群机器人与 IM | 飞书（已有）、**钉钉**（含加签）、**企业微信**、**Slack**、**Discord**、**Microsoft Teams（Workflows webhook）**、**Telegram**、ntfy、Gotify | 首发覆盖国内 + 海外常用群聊 |
| 邮件 | SMTP（**平台界面可配置**，含测试发送） | 换用 `nodemailer`，删除手写 SMTP 客户端 |
| 短信 | Provider 接口 + **阿里云 / 腾讯云 / AWS SNS / Twilio** | 换用官方 SDK，删除手写腾讯云 TC3 签名 |
| WhatsApp | 官方 Cloud API + 预审模板（P3，接口与配置先做） | 需 Business 验证与模板审核，具备条件后启用 |
| 平台 | 通道配置页（凭证加密存储、只写不读、发送测试）、联系人按通道给字段、模板按「通道组」维护、**许可白名单 CI 门禁** | 开源分发要求：零内置凭证、依赖许可干净 |

范围外：语音（Twilio Voice）、PagerDuty 官方 SDK（用通用 Webhook 覆盖）、自建短信网关、每通道独立限流策略的 UI 配置（给默认值即可）。

## 2. 验收标准（门禁要素②）

- [ ] **C-1 通道覆盖**：上述通道均可作为告警联系人并实际投递；`GET /ops/alerts/channels` 返回每个通道的可用性（**未配置凭证 → 不可用**，开源默认全部不可用）。
- [ ] **C-2 平台化配置**：运维 → 监控告警 →「通道配置」页可配置 SMTP、短信各厂商、Telegram bot、WhatsApp；**密钥字段只写不读**（回显仅"已配置"+末 4 位），保存写审计。
- [ ] **C-3 发送测试**：每个通道有「发送测试」按钮，可填收件人/目标，返回成功或**原始错误码**（便于排障）；邮件先 `verify()` 再实发。
- [ ] **C-4 通用 Webhook**：URL / headers / body 可自定义，**body 支持占位符模板**（复用 alerting-v4 引擎），可直接对接 PagerDuty Events API 等第三方。
- [ ] **C-5 钉钉加签**：支持自定义关键词、加签（毫秒 timestamp + `"\n"` + secret → HmacSHA256 → Base64 → urlEncode）、IP 白名单三种安全设置下的投递；加签失败给出可读原因。
- [ ] **C-6 模板分组**：通知模板由「事件类型 × 通道」改为「事件类型 × **通道组**（chat / email / sms）」，默认模板覆盖新通道；旧数据自动映射（飞书 → chat）。
- [ ] **C-7 限流硬约束**：每通道**令牌桶 + 发送间隔**（钉钉/企微 20 条/分钟、Telegram 群 20 条/分钟等），同一轮积压超过阈值时**合并为一条摘要**；不允许因限流导致告警丢失或静默 10 分钟。
- [ ] **C-8 零内置凭证**：仓库与镜像中不含任何厂商凭证或默认 webhook；通道配置为空时功能可正常启动、UI 明示"未配置"。
- [ ] **C-9 许可门禁**：CI 增加依赖许可白名单检查（仅允许 MIT / Apache-2.0 / BSD-2/3 / ISC / 0BSD / Unlicense），违反即失败。
- [ ] **C-10 去重复开发**：邮件改用 `nodemailer`、短信改用官方 SDK；仓库里不再有手写 SMTP 协议实现与手写 TC3 签名（有单测锁死）。
- [ ] **C-11 文档**：`docs/` 补通道配置指南（各通道如何申请凭证、限流与模板注意事项、海外网络与合规提示）。

## 3. 非目标（门禁要素③）

- 不做双向交互（回复告警、确认、静默指令）——Telegram/Slack 只做单向发送。
- 不引入通知聚合框架（Novu / notifme-sdk）与其自托管服务（调研结论：渠道缺口 + 运维成本 + 许可风险）。
- 不使用非官方 WhatsApp 库（违反 ToS）；不做个人号通道（企业微信个人号、Telegram userbot 等）。
- 不做通道凭证的 KMS 集成（本期 AES-256-GCM + 环境变量主密钥，格式预留 key_id 便于将来接 KMS）。
- 不做每通道可调的限流 UI、不做告警去重/抑制策略的改造（沿用 alerting-v1~v4 既有语义）。
- 不做短信/WhatsApp 的模板报备自动化（控制台/工单仍是人工前置条件）。

## 4. 用户可见行为

| 位置 | 变化 |
|---|---|
| 运维 → 监控告警 →「通道配置」 | 新增页签：按通道分组表单（SMTP / 短信 / Telegram / WhatsApp …），含「发送测试」「保存」，密钥只写不读 |
| 运维 → 监控告警 →「联系人」 | 通道类型扩到全量；按通道显示对应字段（Webhook URL / 加签密钥 / chat_id / 手机号 / 邮箱），不可用通道给出原因 |
| 运维 → 监控告警 →「通知模板」 | 由「通道」改为「通道组」：群聊与 Webhook / 邮件 / 短信，三组即可覆盖全部通道 |
| 告警投递 | 每个通道独立限流与失败重试；同一轮积压自动合并为摘要；失败记录保留原始错误码 |
| 开源使用者 | 克隆后默认无可用通道；按文档配置任一道即可收到告警 |

## 5. 风险与前置条件

| 项 | 说明 |
|---|---|
| 凭证与前置审批 | 国内短信签名/模板需报备；AWS SNS 发中国号码需工单、无 cn-* 区域；WhatsApp 需 Business 验证 + 模板审核。这些是**使用者的账号侧流程**，不阻塞代码交付 |
| 跨境网络 | Telegram / WhatsApp 在大陆需代理出口（运维条件） |
| 限流 | 钉钉/企微/Telegram 官方均为 20 条/分钟，检测器一轮可命中多条 → 由 C-7 的令牌桶 + 合并满足 |
| 测试条件 | 本期无法在有真实凭证的环境下跑端到端，交付时提供**手动测试清单**（用户按清单自测） |

## 增补 v1.1（2026-10-09）：通道暂停投递 + 各通道前置条件说明

背景：邮件通道走「平台邮件通道」兜底后，界面上关不掉它——开关的 off 位只表示「本通道自己的配置未启用」，
不代表停发（要停发得先删掉平台邮件通道的配置）。同时 WhatsApp 与四家短信尚无「要准备什么、怎么验证」的说明，
而它们**无法在本环境用真实账号验证**。

**阶段目标与范围（门禁要素①）**

1. **暂停投递**：每个凭证级通道（`smtp` / `telegram` / `whatsapp` / `sms_*`）可被显式暂停——保留配置与密钥，
   但该通道不参与任何投递（**含平台邮件通道兜底**）。
2. **前置条件说明**：为各通道补表头「?」帮助，每份只写三件事——①要准备什么 ②要填什么 ③怎么验证；
   **不写未经核实的控制台操作路径与具体错误码清单**（把猜测写成产品文案比不写更糟）。

**验收标准（门禁要素②）**

- [ ] AC-1 暂停即不可用：`muted = true` 的通道，`channels` 返回 `available = false` 且
      `reason_key = alerting:channel.muted`；联系人下拉里该通道置灰。
- [ ] AC-2 暂停阻断投递：规则触发时该联系人投递记为失败，`error = channel_muted`，且**不进重试**（确定性失败）。
- [ ] AC-3 兜底也被挡住：`smtp.muted = true` 时即使平台邮件通道可用也不发邮件——这才是「真正关掉」。
- [ ] AC-4 恢复即生效：改回 `muted = false` 后无需重启，下一次投递恢复。
- [ ] AC-5 短信多厂商：暂停某一家后，自动挑选（未指定厂商的联系人）跳过它，其余厂商不受影响。
- [ ] AC-6 帮助覆盖：`smtp` / `telegram` / `whatsapp` / 四家短信都有「?」，每份三步（准备 / 填写 / 验证），13 门语言键齐。
- [ ] AC-7 门禁：`i18n_check` / `i18n_scan --check` / `arch_ratchet` / 前后端全量测试 全绿。

**非目标（门禁要素③）**

- 不做暂停的定时/条件化（夜间静默等）——那属于「屏蔽」页既有语义。
- 不改发送侧回落顺序，不改平台邮件通道的配置入口与优先级。
- 不为未验证通道写操作路径与错误码清单；**验证状态矩阵**写在配置指南里，不写进代码注释当结论。
- 不新增接口版本：`muted` 走既有 save 接口的加法式字段。

## 增补 v1.2（2026-10-10）：通道集收敛——删除 5 个 webhook 类通道

**阶段目标与范围（门禁要素①）**：从通道注册表中删除 **Slack / Discord / Microsoft Teams / ntfy / Gotify** 五个通道
（含其联系人校验、发送实现、13 门语言文案与单测），保留飞书 / 钉钉 / 企业微信 / Telegram / 通用 Webhook /
邮件 / 短信 / WhatsApp。删除理由：① 本次可验证范围内无可用账号或服务（Teams 必须用 Power Automate Workflows 需 M365；
Gotify 需自建服务；ntfy/Slack/Discord 需外部工作区）② 生产台账显示无任何联系人使用这五个通道
③ 收敛维护面与「联系人 → 通道」下拉的噪音。

**验收标准（门禁要素②）**

- [ ] AC-1 `channels` 能力位只剩 8 个通道（飞书 webhook / 钉钉 / 企业微信 / Telegram / 通用 Webhook / 邮件 / 短信 / WhatsApp），
      联系人通道下拉不再出现被删的 5 个。
- [ ] AC-2 被删通道不再有注册表条目、发送实现、校验函数与语言键（`sender-push.ts` 整文件移除；
      `alert.channelName.*` 与 `alerting:channel.*` 各语言键同步删除）。
- [ ] AC-3 存留通道行为不变：飞书加签、钉钉加签、企微、Telegram、通用 Webhook、邮件（含平台回落）、短信、WhatsApp 全部用例通过。
- [ ] AC-4 存量数据不失效：`alertcontact` 中不存在被删通道的联系人（生产核对：仅 feishu_webhook ×2 / email / telegram）；
      若历史行仍引用被删通道，投递会记为 `unknown_channel_<kind>` 失败并在「通知记录」可见（不静默）。
- [ ] AC-5 门禁：`i18n_check` / `i18n_scan --check` / `arch_ratchet` / 前后端全量测试全绿。

**非目标（门禁要素③）**

- 不做「按部署可选通道集」的配置化（若将来需要，另开 phase 设计通道开关）。
- 不删除历史文档与验收记录中对这 5 个通道的描述（那是当时的交付事实），只更新**活文档**（README / 使用指南 / 运维手册）。
- 不引入替代通道（如自建 webhook 已可由「通用 Webhook」覆盖）。
