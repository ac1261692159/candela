# PRD：用户分群体验优化与健壮性

> phase A: `clklog-analytics-user-segment-ux-v1`
> phase B: `clklog-analytics-cohort-robustness-v1`
> 前置：`docs/product/prd-clklog-analytics-user-segment-v1.md`、`docs/product/prd-clklog-analytics-user-segment-followups.md`（成员表 / `scope=cohort` / SQL 分群 / 标签 / 分析主体均已上线）
> 下游设计：`docs/architecture/clklog-analytics-design-user-segment-ux-v1.md`

---

## 0. 背景（现状评审结论）

功能已可用，但作为「圈人工具」缺关键的反馈回路，且入口与列表的表达方式让人读不懂：

1. **圈人结果在保存前看不见**。条件分群没有试跑/预估；后端只有 `preview-sql` 与 `preview-result`。用户必须「保存 → 等异步计算 → 回列表看人数 → 再改」，改一条在用分群的条件同样无法预知影响。
2. **列表以机器名为主身份**。首列是 `name`（`cohort_20260905_132959`），显示名退居第二列；没有规则摘要列，看不出这条分群圈的是什么；没有主体列，多主体项目分不清；无筛选、无排序、无分页。
3. **人数不可点**，成员列表藏在「更多」菜单里，且只能看不能查。
4. **入口是纯猜谜**。创建类型弹窗是三个等宽按钮，无说明无场景，第一个还被涂成主色。
5. **计算期间列表每 3 秒整表闪一次 loading**（轮询把 `loading` 打开），失败时列表被清空成空状态。
6. 健壮性缺陷另列 B 段：ID 分群名单不可更新、上传体积上限与后端允许值差两个数量级、删除分群不检查看板引用、计算中状态无崩溃恢复。

## A 段：圈人反馈回路与列表可用性

### A.1 阶段目标与范围

让用户在**保存前**知道这条规则会圈到多少人、与当前已存版本差多少；让**列表**能读懂、能筛、能定位到人；让**入口**讲清楚三种类型分别适合什么。

包含：

1. **条件分群试跑与人数预估**：按当前草稿（未保存也可）实时算一次，返回预估人数与前若干示例 ID；编辑态同时给出与当前已保存人数的差值。
2. **分群列表重做**：显示名为第一列；新增规则摘要列、分析主体列；人数可点开成员；按 类型 / 状态 / 主体 筛选；按 人数 / 最后计算时间 排序；分页；计算中静默刷新不闪 loading。
3. **成员抽屉可检索**：按用户 ID 检索（有界 + 超时），不再只能翻前 1000 行。
4. **创建入口类型卡**：三种类型各给图标、一句话说明与典型场景；并说明「结果分群」从分析结果的人数格保存。

### A.2 验收标准

- [ ] UX-1：条件分群编辑页有「试跑」入口，点击后展示预估人数；未保存的新分群与编辑态均可试跑。试跑不写成员表、不改分群状态。
- [ ] UX-2：编辑已有分群时，试跑结果同时显示当前已保存人数与差值方向（增加 / 减少）。
- [ ] UX-3：试跑返回的示例 ID 最多 20 条，超出提示「仅显示前 N 条」；预估人数为精确值（非抽样估算）。
- [ ] UX-4：条件不完整（未选事件 / 未选属性 / 序列步骤未填满）时，保存与试跑都被拦下，且在对应条件行内联标红提示，不再只弹后端 `conditions[0].event 必填` 式文案。
- [ ] UX-5：列表第一列为显示名，第二列为分群名（机器名弱化）；新增「圈人规则」摘要列，把条件渲染成一句人话（如「过去 7 天做过 AppStart 的次数 大于 0」）。
- [ ] UX-6：列表新增「分析主体」列；主体名取当前项目主体清单，非预置主体显示其显示名。
- [ ] UX-7：列表可按 类型 / 状态 / 分析主体 三项筛选，可按 人数 / 最后计算时间 排序，并分页（默认 20 条/页）。筛选与排序为客户端行为，不新增列表接口。
- [ ] UX-8：人数格可点击打开成员抽屉；抽屉内可按用户 ID 检索，命中结果受 LIMIT 与超时约束。
- [ ] UX-9：计算中轮询为静默刷新——不出现整表 loading 蒙层、不清空已有行；仅首次加载与手动搜索显示 loading。轮询失败保留现有行，不再把列表清空成空状态。
- [ ] UX-10：创建类型弹窗为三张类型卡（图标 + 名称 + 一句话说明 + 典型场景），带「取消」；卡片外说明「结果分群从事件 / 漏斗 / 留存的人数格保存」，并给出跳转分析的引导。
- [ ] UX-11：全部新增文案走 i18n，13 个已上线语言齐备；`python3 scripts/i18n_check.py` 与 `python3 scripts/i18n_scan.py --check` 通过；`python3 scripts/arch_ratchet.py` 通过。

### A.3 非目标

- 不做「保存时自动预演」或后台常驻预估；预估只在用户显式点试跑时执行。
- 不做预估结果缓存、不做历史人数曲线（人数趋势属后续「分群成员趋势」议题）。
- 不改条件分群的**语义**（时间窗仍为 `[D-n, D-1]`、「没做过」的宇宙仍是窗内活跃用户）；语义提示文案也不在本期。
- 不改分析侧选择器与看板分群筛选的行为。
- 不引入服务端分页 / 服务端排序；列表仍是一次取回本项目全部分群（上限 200）。
- 不做列表列显隐拖拽、收藏、批量操作。
- ID 分群与结果分群不做试跑（前者输入即名单，后者是快照）。

## B 段：过程健壮性

### B.1 阶段目标与范围

1. **ID 分群名单可替换**：支持重新上传 CSV 覆盖名单并重算，不必删了重建。
2. **上传体积上限对齐**：分群路由的请求体上限与后端允许的行数相匹配，不再出现「几万行就 413、提示还说服务不可用」。
3. **删除分群引用检查覆盖看板**：看板级分群筛选被引用时，删除确认要说出来。
4. **计算中状态可恢复**：服务重启后自动回收卡在 `pending` 的分群，不再永久转圈。
5. **超大请求体提示可读**：413 有专门文案，不再落到「服务暂时不可用」。

### B.2 验收标准

- [ ] RB-1：ID 分群编辑页可重新上传 CSV；上传后立即重算并覆盖成员，`batch_id` 换新，旧批成员删除；列表人数与最后计算时间随之更新。
- [ ] RB-2：重传失败（CSV 无有效 ID / 超行数上限）时保持原成员不变，状态不被改成 `failed`。
- [ ] RB-3：分群路由的请求体上限提升到与「单次最多 100 万行 ID」相称的量级，并在设计文档写明取值与依据；仍超限时的提示可读（RB-5）。
- [ ] RB-4：删除被看板级分群筛选引用的分群时，确认弹窗列出引用它的看板名；`force` 语义不变。
- [ ] RB-5：超大请求体返回可读文案（各语言齐备），不再是「服务暂时不可用」。
- [ ] RB-6：服务重启后，处于 `pending` 超过既定阈值的分群被自动重新入队计算；回收有数量上限，避免启动风暴；`ready` / `failed` 行不受影响。

### B.3 非目标

- 不做名单**追加**语义（重传即整体替换；要加人请上传合并后的完整名单）。
- 不做 multipart 分片上传、断点续传、上传进度条。
- 不引入独立的作业队列/消息中间件；回收仍用现有进程内计算器。
- 不做删除前的引用影响面「一键清理」，仍由用户决定。
- 不做 `sa_cohort_members` 的成员级审计。

## 体验细则

- 类型卡顺序与现有业务频次一致：条件分群 → ID 分群 → SQL 分群；条件分群不预设主色，三张卡视觉等价。
- 摘要句控件不换行拆字，装不下整句换行（沿用 v1 PRD §4）。
- 摘要里的**事件名、属性名、分群名、标签值是用户自己起的名**，原样显示不翻译；只有句式与比较符走 i18n（`AGENTS.md` G24）。
- 预估人数用千分位；差值为 0 时不显示箭头，只显示「与当前一致」。
- 试跑是显式动作，出现耗时属预期：按钮进入 loading，完成后给出人数与示例。

## 与 v1 / followups 的关系

- `kind`、`definition_json`、成员表、`scope=cohort`、分析主体均不变；本期只增加读取路径（试跑 / 检索）与表达层。
- 条件语义、时间窗算法、批量切换策略不动，因此无数据迁移。
- 后续（不在本期）：条件能力扩展（事件属性子筛 / 按天去重 / 含今日与全部时间）、分群套分群、定时时间可选与完成通知、「用户资产」三页收敛。
