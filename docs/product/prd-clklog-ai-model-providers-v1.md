# PRD：AI 模型供应商网页设置（model-providers）

- `phase: clklog-ai-model-providers-v1`
- 帽子：产品
- 上游：`docs/architecture/clklog-ai-analytics-design.md`（§6 供应商 schema 与密钥出口）、`docs/architecture/clklog-ai-analytics-design-model-providers-v1.md`（实现方案）
- 触发：用户要求「在设置中的 `AI Workspace 管理` 增加供应商设置，用于设置 DeepSeek Harness 的模型供应商，而不是靠配置文件」
- 修订：**v1.1（2026-09-22，同日）**——见文末「v1.1 修订」，删除环境变量密钥机制、供应商改为完全由网页维护（初始为空），并新增「模型是否支持图片输入」
- 修订：**v1.2**——只有「配了密钥 **且** 连接测试通过」的模型才出现在 AI 助手的模型列表里（见文末「v1.2 修订」）

---

## 1. 阶段目标与范围（门禁要素①）

把 Harness 的**模型供应商**从「改 `config_server.yaml` → 提交 → 发版 → 重启进程」改成**超管在网页上增删改**，密钥加密落库，改动不需要发版。

范围（可写）：供应商清单与其模型清单（含**是否支持图片输入**）、`base_url`、协议、密钥，以及**默认供应商 / 默认模型 / 默认思考强度**。

范围（仍只读，留在 YAML）：`deepseek_harness.enabled`、`runtime.*`、`workspace.*`、`defaults.permission_preset`——这些是部署容量与安全预设，不属于「供应商」，改动仍走运维。

**供应商没有任何配置文件来源**（v1.1）：配置文件、环境变量都不再提供供应商或密钥，初始就是空的，超管自己添加、自己填密钥。

| 面向角色 | 能做什么 |
|---|---|
| 平台超管（`ops.ai_workspace.manage`） | 在「AI Workspace 管理 → 模型供应商」页查看来源、增删改供应商与模型、测连接、选默认模型、把配置文件里的供应商一键导入、让改动对运行中的会话立即生效 |
| 普通成员 | 无变化：仍看不到、改不了任何供应商设置 |

## 2. 用户可见行为

| 场景 | 行为 |
|---|---|
| 还没配置过 | 表格为空 + 空状态提示「还没有模型供应商」，主按钮「新增供应商」 |
| 新增/编辑供应商 | 表单填 provider ID、显示名、协议、`base_url`、密钥、模型清单（每行：模型 ID、显示名、**是否支持图片输入**、支持的思考强度、默认思考强度）。校验不过**不落库**并给出本地化原因 |
| 密钥留空保存 | 视为「不修改密钥」，不会把已有密钥抹掉 |
| 一个供应商都没有、或没有任何可用模型时用户开助手 | 明确报错「尚未有可用模型：请配置密钥并测试连接」，不启动一个没有模型的会话 |
| 模型是否可选 | 助手的模型列表**只出现配了密钥且测试通过的模型**；缺密钥或未测过的模型不出现（选了必然失败，不该给用户看到） |
| 点「测试连接」 | 逐个测试该供应商下的**所有模型**，逐个记录结果：通过的进入可选列表，失败的给出厂商原始错误 |
| 密文不可解密（主密钥被换） | 该行与页面顶部**红色**告警，明确要求重新填写密钥；不静默降级、不回退到配置文件 |
| 测连接 | 按该供应商的协议发一次最小真实请求，显示成功/失败、HTTP 状态与耗时；失败时展示厂商原始错误（不含密钥） |
| 选默认模型 | 供应商 → 模型 → 思考强度三联联动；三者必须自洽（默认思考强度必须在该模型支持集合内） |
| 保存成功 | 明确告知「新建会话立即生效；**N 个运行中的会话**仍用旧配置，下次打开助手时自动切换」，并提供「立即应用并重建 (N)」按钮（二次确认，明示会中断这些会话） |
| 删掉正在被默认引用的供应商 | 拒绝保存并说明原因（默认供应商必须存在） |
| AI 未启用（`enabled: false`） | 页面仍可进入与编辑（配置先备好），顶部提示 AI 未启用，调用侧不受影响 |

## 3. 验收标准（门禁要素②）

- [ ] **MP-1**：`AI Workspace 管理` 页出现第 4 个 Tab「模型供应商」，仅超管可见可操作；普通成员既看不到 Tab，也调不通对应接口（403）。
- [ ] **MP-2**：未导入时来源显示「配置文件」；点导入后来源变为「设置页」，且导入后的展示名、协议、`base_url`、模型清单与配置文件逐项一致。
- [ ] **MP-3**：导入后**发版不改任何配置文件**也能改供应商：改 `base_url`/模型清单/密钥并保存，关闭再打开助手（重建运行时）后实际走新配置，网关审计行记录新目标。
- [ ] **MP-4**：非法输入一律**拒绝且库内无变化**：provider ID 非法、模型 ID 重复、思考强度为空、默认思考强度不在支持集合、`base_url` 非 HTTPS（loopback 除外）、删除默认供应商、默认模型不在清单内、把最后一个供应商删光。
- [ ] **MP-4b**：模型勾选「支持图片输入」后，会话生成器写入的模型画像声明 `input: ['text','image']`（未勾选为 `['text']`），DSH 侧按该声明接受图片附件。
- [ ] **MP-5**：测连接对可用供应商返回成功与耗时；对错误密钥返回失败并带厂商原始错误，且**任何响应/审计里都不出现密钥明文**。
- [ ] **MP-6**：惰性生效成立——保存后运行中会话继续可用；「立即应用」回收数量等于当前运行中的 Harness 会话数。
- [ ] **MP-7**：默认模型改动对**已存在用户**生效（重开助手即用新默认模型），且该用户 `dsh-home` 下 `settings.yaml` 的其他键不丢失。
- [ ] **MP-8**：`config_server.yaml` 中不再出现明文供应商密钥，AI 仍可用；接口与页面均不回显明文（仅 `••••末4位`）。
- [ ] **MP-9**：相关自动测试、两端构建、`python3 scripts/arch_ratchet.py`、`python3 scripts/i18n_check.py`、`python3 scripts/i18n_scan.py --check` 全绿；浏览器实测（zh-CN 与 en-US 至少两种）无原文残留。

## 4. 非目标（门禁要素③）

- 不开放普通用户选择或新增模型/供应商（保持「普通用户只读」）；不恢复 DSH 官方 `ui-settings-models` 插件。
- **不提供任何环境变量或配置文件的密钥覆盖**（v1.1）：密钥只有「设置页密文」一个来源；`api_key_env` 与 YAML `providers` 一并删除。
- 不做「已验证」的**到期失效**（v1.2）：验证只在供应商配置被改写时清空，不按时间过期；模型能力变化（厂商下线、额度耗尽）由下一次测试暴露。
- 不改 `enabled` / `runtime.*` / `workspace.*` / `permission_preset`（仍 YAML + 运维），网页只读展示。
- 不做供应商级限流、token 预算、计费、用量统计（网关既有每运行时限流不变）。
- 不接 KMS / 不自动轮换密钥 / 不做多主密钥并行解密（沿用 `ALERT_CONFIG_KEY` 单一主密钥）。
- 不新增 `adapter` / `protocol` 枚举（仍是 `openai_compatible|deepseek` × `openai-completions|openai-responses|anthropic-messages`）。
- 不改容器隔离、capability 机制、网关代理与模型 allowlist 的判定逻辑（只把配置来源从 YAML 换成「库优先」）。
- 不改 Puppet/安装脚本对 `runtime.*`、`workspace.max_bytes` 的读取（那些键仍在 YAML）。

## 5. 边界与残余风险（面向使用者说明）

1. **密钥仍会经过浏览器**：填写时由超管浏览器提交到平台（HTTPS）。平台只以密文存储、只回显末 4 位，但「谁填谁知道」这一条不因本功能改变。
2. **主密钥变更会使旧密文不可解密**：变更 `ALERT_CONFIG_KEY` 后，页面会显式报「密文不可解密」，需要重新填写密钥（与告警通道、邮件通道同策略）。
3. **仓库历史里的旧明文密钥**：本功能把配置文件里的明文清空，但**不会**清除 Git 历史中的旧值，两个真实密钥需要在功能上线后轮换（另行安排）。
4. **改动即影响所有用户**：供应商与默认模型是平台级设置，保存后所有用户的新会话都受影响。

## 附：v1.1 修订（2026-09-22，同日）

用户决策（原话）：「我现在不需要环境变量，把这个设计删了，模型供应商现在有的不动他，设计上模型供应商是空的，
需要超管自己去添加，秘钥自己去填，不依赖环境变量，老的那一套环境变量模式完全删除，并且在这里可以配置
模型能力是否支持图片输入」。

| 变更 | 内容 |
|---|---|
| 删除环境变量密钥机制 | 删掉 `api_key_env` 与 `env[api_key_env]` 覆盖；密钥只有「设置页密文」一个来源。数据库删除该列，配置 schema 与页面同步移除 |
| 删除配置文件的供应商来源 | 删掉 `deepseek_harness.providers` 与 YAML 里 `defaults.{provider,model,reasoning_effort}`；不再有「从配置文件导入」，供应商**初始为空** |
| 保留既有数据 | 平台上已导入的两个供应商行不删除、不改动（用户明确「现在有的不动他」） |
| 新增模型能力：图片输入 | 每个模型一个「支持图片输入」开关，落库后进入会话生成器的模型画像（`input: ['text','image']`），DSH 据此接受图片附件 |
| 未配置时的行为 | 一个供应商都没有时，用户开助手直接给明确提示，不启动没有模型的会话 |

验收补充（在 §3 的 `MP-*` 之外）：**MP-4b** 图片能力贯通（见上）；**MP-10** 全库无 `api_key_env`
（`rg "api_key_env" apps/ scripts/` 无命中）且全新部署无需任何环境变量即可添加并使用供应商。

## 附：v1.2 修订（2026-09-22）

用户反馈（原话）：「没有配置秘钥和没有测试成功的模型，不应该在 harness 里可被选择」。

现象：助手右上角的模型列表把两个供应商的 4 个模型全列出来了，其中 `DeepSeek Official` 连密钥都没配、
`Tencent TokenHub` 也没测过——用户选了必然失败，属于「给了不该给的选项」。

| 变更 | 内容 |
|---|---|
| 可用模型 = 有密钥 **且** 测试通过 | 逐模型记录测试结果（`verified_models_json`）；生成会话配置时只下发可用模型，供应商若一个可用模型都没有则整条路由不下发（DSH 侧连组名都不出现） |
| 「测试连接」改为批量 | 一次测试该供应商下所有模型，逐个记录；返回逐模型结果，界面汇总「n/m 可用」，失败项给厂商原始错误 |
| 配置改写即失效 | 供应商的地址/协议/密钥/模型清单被编辑后，此前通过的验证全部清空（改完必须重测）——避免「改了地址但验证还是旧的」 |
| 默认模型 | 只能选可用模型；存量默认不可用时自动退到第一个可用模型，会话配置不会被写坏 |
| 网关联动 | 模型出口网关的 allowlist 取自同一份有效配置，未验证模型即使被伪造请求也会被 400 拒绝 |

验收补充：**MP-4c** / **MP-4d**（见上）。注意这是一次**有意的行为收紧**：升级后如果还没有任何模型测试通过，
助手会直接提示「尚未有可用模型」，需要超管先点一次「测试连接」。
