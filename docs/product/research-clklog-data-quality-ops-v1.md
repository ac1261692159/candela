# 调研：数据质量 × 数据运维 的关系、对拍实测结论与推进计划

- `phase: clklog-data-quality-ops-v1`
- **本文件是调研（事实与证据）；正式门禁文档已落地**：PRD `prd-clklog-data-quality-ops-v1.md`（R1/R2/R3 + 12 条验收）、设计 `clklog-analytics-design-data-quality-ops-v1.md`（配置表 / 清理登记 / 可信区间 / 定时与前置对拍契约）
- 相关：`prd-clklog-analytics-v1-data-governance.md`、`clklog-analytics-design-data-governance.md`（对拍口径 SSOT）、`prd-clklog-analytics-data-management-v1.md`（数据运维）、`clklog-analytics-design-ops-console-v1.md`
- 调研时间：2026-10-08（生产只读实测，未做任何写操作、未发版、未重启）

## 1. 两者到底是什么关系

| 维度 | 数据质量（数据管理 → 数据质量，`/sa/meta/quality`） | 数据运维（运维 → 数据运维，`/sa/ops/data-management`） |
|---|---|---|
| 唯一问题 | 数据**对不对**（完整性 / 一致性） | 数据**占多少、留多久、能否回收** |
| 能力 | 一致性对拍（总量 / 事件级 / CRC / 抽样）、元数据发现变化 | 存储盘点、增长趋势、清理预演与执行（DROP PARTITION）、TTL、目录日志清理、动作审计 |
| 数据源 | `clklog_sa.sa_events` ⟷ `clklog.log_analysis`（只读，跨库） | `system.parts` / `system.tables` + 目录文件 |
| 结论载体 | 快照 `ops_reconcile_snapshot`（MySQL） | 动作审计 `ops_action_log` |

三处**实际耦合**（代码级，不是概念上的）：

1. **数据运维页的「健康」卡片直接复用对拍快照**：`GET /ops/data-mgmt/health` → `DataMgmtService.latestSnapshot()`，与质量页读同一张表 → 两个页面同时过期、同时"正常"。
2. **保留策略决定对拍的可用区间**：对拍能比的范围受两侧保留期约束（见 §3.7）。
3. **对拍应当是清理的安全前置**：清理（DROP PARTITION / TTL）会改变数据；执行前应有「该范围最近一次对拍通过」的判据，执行后应登记「已清理区间」让对拍自动跳过。**目前两者完全没连线**（既无前置检查，也无区间登记）。

另有 1 处死代码：`DataMgmtService.saveReconcileSnapshot()` 无任何调用方（CLI 与页面都不用它）。

## 2. 对拍在真实环境是否有效（实测）

**结论：机制能跑、判定能触达，但作为「监控手段」当前基本无效**——没有定时、结论陈旧、阈值形同虚设、且基准本身口径可疑。

### 2.1 机制验证（低量日期，零负载）

| 用例 | 命令（在服务器上跑仓库内脚本，凭据走环境变量） | 结果 |
|---|---|---|
| 正常日 | `bash -s -- --type=count --from=2026-11-01 --to=2026-11-01 --threshold=0.001` | `119 = 119 = 119`，偏差 0.00%，`ok`，退出码 0 ✅ |
| 差异日 | 同上，`--from=2026-11-08` | `sa 199 / raw 179`，偏差 **11.17%**，`ALERT` + 「存在超阈值偏差」，退出码 1 ✅ |

→ 脚本的参数、SQL、阈值判定、退出码、报告输出都可用（选低量日期是为了不给 12GiB 的 ClickHouse 容器加负载；未跑整日全量）。

### 2.1.1 附带发现：对拍的 raw 侧 SQL 无法分区剪枝（定时化前值得一并修）

`clklog.log_analysis` 的分区键是自带的 `stat_date`（**按日分区**，90 个分区 / 47.9 GB），而对拍 raw 侧写的是 `WHERE toDate(log_time) BETWEEN …` —— 表达式不是分区键，ClickHouse 无法剪枝，**单日对拍也要扫全部 90 个日分区**。改用表自带的 `stat_date` 后，单日对拍只命中 1 个分区。

实测两者在 2026-10-07 计数完全一致（`stat_date` 与 `toDate(log_time)` 均为 千万级），因此这是**纯收益的口径修正**：对拍范围上限（现为 3 天）与单机 12 GiB 容器的负载约束都能放宽。R1 落地时用 `system.query_log.read_bytes` 对比前后，作为量化证据。

### 2.2 没有定时：设计承诺的「每小时/每日」从未落地

- root crontab：只有腾讯云 agent、weblogs 清理、mysql 备份——**没有 reconcile**；`/etc/cron.d` 也没有。
- supervisor：只有 analytics-server / ingestor / harness-broker，无对拍程序；设计里写的小时级报告目录 `logs/reconcile/` **不存在**。
- 唯一入口是质量页的「开始对拍」按钮（人工）。

### 2.3 结论陈旧且在两个页面同时展示为「正常」

- `ops_reconcile_snapshot` 共 **7 条**，最后一条 **2026-09-21 12:25**（今天 2026-10-08，已 17 天）。
- 质量页原样显示「**数据一致性正常** · 2026-09-19 ~ 2026-09-19 对拍偏差均在阈值 10% 内」，**没有任何「结果已过期」提示**。
- 数据运维页的「健康」读同一快照 → 同样过期。
- 结果是：运维看到的「健康」是 17 天前的结论，而期间数据每天新增 ~3,500 万行。

### 2.4 阈值与设计不一致，实际灵敏度极低（最关键的发现）

- 设计文档：`ABS(sa-raw)/raw > {threshold}`，**默认 0.1%**。
- 实现（服务与 CLI 同为）：`status = absDev > threshold * 100`，默认 `threshold=0.1` → **实际阈值 10%**；页面上也直接写着「阈值 10%」。
- 实测**完整日**差异（按两表自带的 `stat_date` 对齐，避免取到仍在写入的当日）：
  - 2026-10-06：sa **千万级** vs raw **千万级** → **+1.39%**（+490,597 行）
  - 2026-10-05：sa **千万级** vs raw **千万级** → **+1.08%**（+394,110 行）
  - 快照里的 2026-09-19（完整日）为 **+1.33%**
  → **稳定存在 1.1~1.4% 的日常偏差**，在 10% 阈值下永远不会告警。
- 两个"顺理成章"的解释已被实测排除：① **不是跨日边界/时区问题**——`log_analysis` 自带的 `stat_date` 与 `toDate(log_time)` 在 2026-10-07 完全一致（千万级 vs 千万级）；② **不是采集延迟**——2026-10-07 当天测得 sa 比 raw 多，一度怀疑是两侧写入速度不同，但 10-05/10-06 这两个**已完结的整天**差异依旧（+1.08% / +1.39%）。
- 换句话说：现在只有「断流/腰斩级」（>10%）故障能被发现；**每天约 49 万行的缺口是隐形的**。而按设计想要的 0.1% 收紧阈值，今天开始就会每天告警——所以不能只改阈值，必须先做 §2.5 的口径归因。

### 2.5 两侧口径不对称：「谁多谁少」目前无法归因

单日（2026-10-07）事件级差异 Top（sa − raw）：

（2026-10-07 当天快照，非完整日）

| 事件 | sa_events | log_analysis | 差 | 相对 |
|---|---|---|---|---|
| base_network_socket_reconnect_start | 276,738 | 176,854 | +99,884 | **+56%** |
| base_network_socket_reconnect_error | 96,479 | 20,553 | +75,926 | **+369%** |
| base_performance_httprequest_report | 千万级 | 千万级 | +57,012 | +0.4% |
| android_gateway_error | 43,626 | 6,722 | +36,904 | **+549%** |
| $AppEnd | 43,165 | 15,168 | +27,997 | +185% |

**完整日（2026-10-06）复核，结论不变**：

| 事件 | sa_events | log_analysis | 相对 |
|---|---|---|---|
| base_network_socket_reconnect_start | 289,273 | 183,438 | **+57.7%** |
| android_gateway_error | 38,500 | 5,813 | **+562%** |

→ 这些事件级差异是**结构性**的（整天、多天复现），不是延迟或边界造成的。总体只差 1.4%、但少数事件差 50%~560%，说明差异集中在特定事件的**计数语义**上（社区侧更少、且同用户同秒存在多行），不是均匀丢失。

对 `reconnect_start` 做重复度对照：

| 侧 | 行数 | 唯一「用户×秒」 | 说明 |
|---|---|---|---|
| sa_events | 276,738 | 275,497（99.5%） | 近乎一条上报一行 |
| log_analysis | 176,854 | 120,405（68%） | 同用户同秒存在大量多行 |

→ 两侧**行级结构完全不同**：社区版侧既不等于我们，也不是"更干净"的基准。因此「sa 比 raw 多」无法判断是**我们的 at-least-once 重复**还是**社区版侧丢失/合并**。当前对拍只在一个方向上可信：**sa 明显少于 raw ⇒ 我们大概率丢了**。

另有一处口径不对称会**制造假告警**：raw 侧 SQL 硬过滤 `event != ''`，sa 侧不过滤。2026-10-07 raw 有 51,490 行空 event；低量日被放大（2026-11-08 的 20 行差里 5 行来自这里，占 2.8 个百分点）。

### 2.6 元数据发现日志是活的（质量页唯一"新鲜"的部分）

`metadiscoverylog` **122,964 条**，最新 **2026-10-08 14:52**（今天）。但质量页只在快照里展示它（快照不存发现日志）→ 页面显示「共 0 条」，需要点「开始对拍」才看得到。

### 2.7 保留策略一侧有、一侧没有（磁盘风险的根）

| 表 | 引擎 / 分区 | 分区数 | 最早 / 最晚 | TTL |
|---|---|---|---|---|
| `clklog_sa.sa_events` | ReplacingMergeTree / **月** | 13 | 202509 / 202709 | **540 天** ✅ |
| `clklog.log_analysis` | MergeTree / **日** | 90 | 2019-09-07 / 2027-09-19 | **未设置** ❌ |
| 社区版 19 张聚合表 | — | 66 左右 | — | **全部未设置** ❌ |

- `log_analysis` 每天约 **+2 GB**（08-28 起每日 1.7~2.0 GiB），**没有任何清理**；页面提示「按日分区不支持月分区清理，请用 TTL」，而 TTL 也没设 → 磁盘直线上涨。
- 两张表都有**脏日期分区**（2019/2023/2027 的测试数据；sa 202709 有 209 KB、log_analysis 2027-09-19 有 58 KB）→ 任何大范围对拍都会误报，清理预演也会撞上「未来分区被拒」。
- **清理执行与 TTL 设置从未在生产执行过**：动作审计里 0 条 `partition/ttl` 记录，只有 `log_cleanup`（目录级日志清理，receiver 日志保留 3 天，今天 14:24 仍在跑）。

### 2.8 实测约束（为什么所有动作都要小步走）

- ClickHouse 容器 **12 GiB** 上限；实测本机使用 **6.9 ~ 8.9 GiB（57% ~ 74%）**、CPU 长期 150% 上下——这是**单机贴顶运行**。
- 代码注释记录 2026-09-07 **两次 OOM 事故**（`uniqExact` + 后台 merge 把容器打死），因此对拍现状：默认单日、上限 3 天、CRC 用 `uniqCombined(20)` 近似 + 0.5% 容忍、大范围对账「预留低峰期专项任务」。
- 本次调研也遵守同一约束：只做低量日对拍 + 单日聚合查询，未跑整日全量对拍、未重启任何服务。

## 3. 推进计划

按"先让结论可信 → 再让关系闭环 → 最后让对拍真正有灵敏度"推进，三个阶段都能独立交付。

### P0 — 让现有结论可信（预计 1~2 天，纯增量、无风险）

| # | 事项 | 验收 |
|---|---|---|
| P0-1 | **对拍定时化**：Puppet 托管一个低峰期每日任务（如 03:30），默认对拍昨日单日；写快照 + 报告落盘（`logs/reconcile/`）。注意仓库已有「文档提交跳过 CI 构建」规则，本项是代码/配置改动，会正常出产物 | 连续 2 天快照 `ran_at` 落在当日；报告文件存在；`puppet agent -t` 后配置可复现 |
| P0-2 | **过期与失败可见**：快照 >24h 标黄、>72h 标红并在质量页与数据运维页同时提示；对拍失败（退出码≠0）走既有告警通道（飞书） | 造一个 3 天未对拍的库，两页都出现红标；手动把阈值调到必失败，收到飞书 |
| P0-3 | **阈值口径统一**：设计/实现/页面三处一致（`threshold` 单位与默认值写死在一处），并把「已知口径差异」显式配置化（空 event 过滤规则、忽略事件白名单），而不是靠 10% 大阈值掩盖 | 三处文案与实现一致；开关改一行即生效；单测覆盖阈值=0 的边界 |
| P0-4 | 清理 `DataMgmtService.saveReconcileSnapshot` 死代码或接上唯一写入方（避免两处写快照） | 代码里只剩一处快照写入 |

### P1 — 把「质量 ⟷ 运维」的关系闭环（预计 1 周）

| # | 事项 | 验收 |
|---|---|---|
| P1-1 | **保留策略总览**：把三类回收动作（月分区 DROP / TTL / 目录日志）合成一张表，并标出「对拍可信区间 = now − min(两侧保留期, 90 天)」 | 页面上能一眼看到每张表的保留期与可信区间；sa 540 天 vs raw 无保留的错配被高亮 |
| P1-2 | **社区版表补 TTL**（`log_analysis` + 19 张聚合表，按业务定 90/180 天），走 Puppet + 演练 | 生产 `system.tables` 显示 TTL；连续 2 天磁盘增长曲线变平；审计留痕 |
| P1-3 | **清理与对拍联动**：① 清理执行前校验「该范围最近一次对拍通过」，未通过拒绝执行；② 清理后登记「已清理区间」，对拍自动跳过这些日期（避免把清理当成丢数） | 构造「对拍失败 + 尝试清理」被拒；清理区间内的日期在对拍报告里标注为「已清理」而非 ALERT |
| P1-4 | **清理执行补验收**（PRD DM-AC8 遗留）：先在**独立测试环境**演练（仓库内已有 `scripts/standalone-test-env/`：`deploy-middleware.sh` + `deploy-clklog.sh` + `verify.sh`，默认目标 `root@<目标机>`）→ 生产一次真实 DROP PARTITION（选最老的脏日期分区）→ 审计 + 回滚预案 | 审计含执行前分区快照；被删分区在 `system.parts` 消失且业务查询无影响；演练环境跑通整链 |
| P1-5 | 脏日期分区清理（2019/2023/2027 的测试数据，两张表） | 对拍在任何范围都不再因脏数据误报 |

### P2 — 让对拍真正有灵敏度（预计 2~3 周，需要先出结论再收紧）

| # | 事项 | 验收 |
|---|---|---|
| P2-1 | **口径对齐白皮书**：用抽样 + 位点对账回答「1.4% 差在哪」——空 event、去重语义、时区边界、Kafka/receiver 计数 | 每个差异来源都有量化结论与判定方法；结论落 `docs/product/` 与 `docs/architecture/` |
| P2-2 | **双向对拍**：行数之外增加「抽样行内容一致率」与「上游计数对账」（receiver 日志/位点），能区分「我们重复」vs「基准丢数」 | 给定一天的差异能给出归因结论，而不是"我们多/它少" |
| P2-3 | **阈值收紧**：口径对齐后把默认阈值降到 0.1~0.5%，并把「稳定基线偏差」写成随表格（例如按事件设阈值） | 收紧后连续 7 天不误报；人为注入 1% 缺口能被发现 |
| P2-4 | **事件级差异进快照 + 页面可视化**（现在快照不存事件级明细，页面永远「暂无数据」）；发现日志页面直读（不等快照） | 页面不点「开始对拍」也能看到最近一次事件级 Top 差异与今日发现变化 |
| P2-5 | 大范围对账的**低峰期专项任务**（设计里"预留"的那块）：分批扫描 + 限内存 + 断点续跑 | 能对账 30 天且 CH 容器内存峰值不超过阈值（实测验证不 OOM） |

### 明确不做（非目标）

- 不把社区版 `log_analysis` 当唯一真值——它自身的完整性尚未证明；对拍定位为「发现方向性异常」而非「裁决谁对」。
- 不做全量行级对拍（12 GiB 容器 + 两次 OOM 的历史）。
- 不对社区版库做任何写操作（红线 1）：TTL 由社区版表自身设置（`ALTER TABLE ... MODIFY TTL`，属社区版表结构变更，需用户明确授权并走 Puppet/演练）。
- 不改动现有对拍 SQL 的只读性质（全部 SELECT）。

## 4. 风险与依赖

| 风险 | 影响 | 缓解 |
|---|---|---|
| ClickHouse 单机 12 GiB、日常 60~75% 占用 | 大范围对拍/清理会 OOM 打死容器（历史两次） | 一切动作单日/小批、低峰期、限内存；P2-5 前先做内存压测 |
| 对拍定时化会新增每日固定负载 | 与业务查询抢资源 | 放 03:30 低峰、单日、串行执行 |
| 阈值收紧前先动阈值 | 每天误报 → 运维忽略告警 | 先做 P2-1/P2-2，再收紧（P0-3 只统一口径不收紧） |
| 清理无对拍基线就执行 | 误删不可恢复 | P1-3 前置校验 + 审计 + staging 演练 |

## 5. 建议的下一步

先做 **P0（1~2 天，零风险且立刻消除"过期结论当现状"的问题）**，同时并行推进 **P2-1 口径对齐调研**（它决定后面能不能收紧阈值）。P1 的社区版 TTL 需要用户授权（涉及社区版表结构变更），建议在 P0 交付后单独确认。
