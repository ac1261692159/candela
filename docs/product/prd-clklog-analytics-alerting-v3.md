## 1. 背景

2026-09-15 的线上验收把告警从「没做过」推到「能响」，但同一轮验收暴露的问题指向另一个层次：**这套告警现在不可运维**。

| 现象（有据可查） | 后果 |
|---|---|
| `slow_query_spike` 因时间窗 bug 连续误报 8 天，期间**没有任何机制发现「这条规则一直在响」** | 规则常亮被视为理所当然，「狼来了」效应 |
| 验收前 `alertcontact` 表为空，8 天告警事件**一条都没外发**，页面无提示 | 告警静默失效，无人知晓 |
| 卡片指标规则引用的卡片被删/缓存长期失败时，`evalCardMetric` 返回 null → 规则**静默失效**（`alert-detector.service.ts:287-300`） | 你以为有人在看着，实际没有 |
| 阈值/联系人/屏蔽的变更**无审计** | 谁把阈值从 20 改成 0 查不到 |
| 通知发送失败**只落一条 `status='fail'`**，无重试、无上层提示 | 告警的可用性本身没有监控 |
| 平台已能算出「磁盘预计 YYYY-MM-DD 用尽」，但**没有任何规则消费这个预测**；`disk_space_low` 只看当前剩余百分比 | 磁盘增长快时，「等到快满了才响」太晚 |

**目标一句话**：让告警从「能响」变成「可信、可查、可依赖」——坏掉能被发现，改动能被追溯，发不出去能被知道，该响的（预测线）能响。

## 2. 用户与权限

仍仅平台超管（`platform_role = super_admin`），路径仍为 `/ops/alerts`。本 phase 不引入新权限码。

## 3. 范围

### 3.1 G1 规则健康度与失效提示

- 规则列表每条带**健康状态**：`正常` / `引用失效`（卡片已被删除）/ `缓存不可用`（卡片在但缓存缺失、报错或超 30 分钟未刷新）/ `无联系人`（未指定联系人且没有默认联系人）。
- 概览 Tab 顶部按需出现提示条（有则显示，无则不打扰）：
  - 没有任何联系人 → 「未配置联系人，所有告警只在页面内可见」
  - 存在失效规则 → 「N 条规则当前无效」+ 可跳转策略 Tab
  - 近 24 小时有通知失败 → 「通知投递失败 N 次」
- 策略 Tab 的规则行内以标签展示健康状态与原因（hover 显示细节）。

### 3.2 G2 配置变更审计

- 以下变更写审计（who / when / what / 变更前后）：
  - 规则：改阈值、比较符、级别、粒度、持续、重复间隔、恢复通知、联系人、启停；新建/删除分析指标规则
  - 联系人：新建、删除、设为默认
  - 屏蔽：新建、删除
- 审计表复用 `ops_action_log`（action 前缀 `alert_`），**不写入任何密钥**：联系人只记脱敏后的地址。
- 页面新增「变更记录」Tab：时间、操作者、动作、对象、变更内容（前后值）。
- 数据运维页的「清理动作审计」卡片**不得**混入告警审计行。

### 3.3 G3 通知投递可靠性与可见

- 单次通知失败后**自动重试**，最多 3 次尝试（退避 1s / 2s），全部失败才记 `status='fail'`。
- 重试过程写日志（规则码 + 第几次），最终结果仍只落**一条** `alertnotification`（保持记录可读）。
- 概览的健康提示含「近 24 小时通知失败数」（见 G1）。
- **检测器防重入**：一轮检测未结束时不再叠加下一轮（重试会拉长单轮耗时，必须防并发导致的重复事件与重复通知）。

### 3.4 G4 预测线告警（第 7 条内置规则）

- 新增内置规则「磁盘预计用尽」：阈值单位**天**，默认 `30`，比较符 `<`（剩余天数少于阈值即告警）。
- 观测值 = 由磁盘用量采样（`disk_used:/data`）线性回归外推得到的**距用尽天数**。
- 不预测的情形（本轮不触发，且**解除已在触发中的事件**）：
  - 采样点 ≥3 且**无增长趋势**（斜率 ≤ 0）→ 视为「不会用尽」，不告警
  - 已越过总量 → 视为 0 天，告警
- 数据不足（采样点 <3）或读取失败 → 本轮跳过（不改状态），与既有规则的「观测失败」语义一致。
- 规则集合仍由版本种子决定：新增后共 **7 条内置规则**，同样不可增删，可启停调阈值。

### 3.5 G5 一次性说明（非新增能力）

- 本 phase 不改变 60 秒检测周期、不改变状态机语义（连续窗口、重复间隔、屏蔽均沿用）。

## 5. 非目标

1. **不做**企微 / 钉钉 / 电话 / Slack 通道。
2. **不做**环比昨天/上周、同比、预测线之外的复杂条件（本 phase 只补磁盘预测这一条）。
3. **不做**告警自动处置（不重启、不清理、不扩容）。
4. **不做**自定义新指标（规则集合仍由版本种子 + 卡片指标规则构成）。
5. **不做**联系组 / 值班表 / 升级策略（escalation）/ 告警认领（ack）。
6. **不做**通知模板编辑（文案仍由代码生成）。
7. **不做**阈值自动标定或基线推荐（本 phase 只提供「值的历史」以外的可见性；基线能力另开 phase）。
8. **不做**Kafka lag / ingestor 心跳（仍沿用 CH 侧 `system.parts.modification_time` 判据）。
9. **不引入** Prometheus / Grafana。

## 6. 关键产品决策

| 决策 | 选择 | 理由 |
|---|---|---|
| D1 | 健康状态由后端算、前端只展示 | 判定依赖卡片/缓存/联系人真实状态，放前端会与检测器口径不一致 |
| D2 | 审计复用 `ops_action_log`，不新建表 | 一处查全部运维动作；用 `alert_` 前缀隔离，避免污染数据运维视图 |
| D3 | 重试只做 3 次、不落多条记录 | 通知记录是给人看的：一次投递事件一行；重试细节进日志 |
| D4 | 「无增长」视为不会用尽（触发解除），「数据不足」视为未知（跳过） | 前者是明确结论，后者是暂时状态；两者混同会让事件永远挂着或误解除 |
| D5 | 预测线只做磁盘一条 | 已有外推能力与采样基础，是当前规则集最大空白；其它预测留待有需求时另开 |
