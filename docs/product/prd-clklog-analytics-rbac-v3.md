# PRD：项目权限口径修正 v3（选择器与治理分离 / 指标归属）

> phase: clklog-analytics-rbac-v3
> 上游：`docs/product/prd-clklog-analytics-rbac-v2.md`（五角色预置与权限目录）、`docs/product/prd-clklog-analytics-account-lifecycle-v3.md` §「增补 v3.2」（本期待修正的那次口径修订）
> 下游：`docs/architecture/clklog-analytics-design-rbac-v3.md`
> 本文是产品层权威：分析师到底能看见什么、能改谁的指标。权限码、守卫落点、API 契约以架构文档为准。

---

## 1. 背景：v3.2 补丁的三个副作用（2026-09-18 验收实测）

v3.2 为解决「邀请注册的分析师在分析页元数据接口 403」，把整个 `meta.view` 授给了分析师。`meta.view` 是元数据域的总钥匙（明细含事件、属性、虚拟对象、**Debug、数据质量**），一次授权同时放开了四类本该属于治理面的能力，并暴露出一个既有实现缺口。验收实测确认：

| # | 现象 | 与 SSOT 的冲突 |
|---|---|---|
| 1 | 分析师侧栏出现「埋点管理」与「数据管理」两个分组，可进 Debug、数据质量、数据表、接入指南，并可直接触发**对拍**重查询 | v2 PRD §6.4「埋点 / 元数据 = 无。侧栏不出现埋点管理」、§10.1 菜单裁剪表「埋点管理：分析师无」 |
| 2 | Debug 读的是 `sa_events` 原始行，未走数据权限（DataScope） | v2 设计文档 §2 验收「读路径统一走 DataScope」；对挂数据权限策略的分析师构成旁路 |
| 3 | 分析师可**删除/编辑他人**的指标 | v2 PRD §6.4「指标管理 · 编辑：新建、编辑、删除**自己的**指标」；权限目录里 `metric.edit_others` 从未被任何代码消费 |

现象 1、3 属实现缺陷；现象 2 属既有缺口（v3.2 之前仅 owner / 分析管理员可达），本期不修，只登记（见 §4 非目标）。

---

## 2. 阶段目标与范围

本期做三件事，只动「权限口径」与「写入口判定」，不动数据模型：

1. **元数据「选择器读取」与「治理」分离**：新增一枚只读权限码，只覆盖分析/分群/标签/指标页在运行时真正调用的元数据读接口；分析师的 `meta.view` 收回，治理面（Debug、数据质量、对拍、数据表管理、接入指南、元事件/属性/虚拟对象管理页）回到 owner 与分析管理员档。
2. **指标写操作按归属判定**：owner / 分析管理员可写任意指标；其余人只能写自己创建的指标（指标不走锁定，因此不引入锁定/授权语义）。
3. **侧栏「数据管理」分组按子项权限裁剪**：分析师只保留「指标」一项；其余子项与「埋点管理」分组对分析师整体消失。

---

## 3. 验收标准

- [ ] **RB3-1 选择器可用**：分析师账号能完整走通事件分析、漏斗、留存、自定义 SQL、分群、标签、主体、指标创建，过程中不出现 403（元数据选择器、维度表属性、值标签加载全部可用）。
- [ ] **RB3-2 侧栏裁剪**：分析师侧栏**无**「埋点管理」分组；「数据管理」分组下**只有**「指标」；「接入指南 / Debug / 数据质量 / 数据表」不出现在分析师侧栏，直链进入被路由门拦下。owner / 分析管理员侧栏与现状一致（两个分组、五项齐全）。
- [ ] **RB3-3 治理面拒止**：分析师直连 `GET /api/meta/quality/reconcile`、`/meta/quality/report`、`/meta/quality/snapshot`、`/meta/quality/discovery-logs`、`/meta/debug/recent`、`/meta/datatables`（列表/详情/使用）、`/meta/event-attributes/:propKey` 全部 403；`meta.edit` 类写接口仍 403。
- [ ] **RB3-4 选择器读接口放行**：分析师对 §2 第 1 条登记的**选择器读接口清单**（架构文档 §5 表，共 8 条）返回 200；清单外任何元数据读接口不得因本次改动变 200。
- [ ] **RB3-5 指标归属**：分析师新建指标成功；编辑、删除**自己的**指标成功；编辑或删除**他人**的指标 403，且前端给出可读提示（非裸 403）；owner 与分析管理员对任意指标可改可删，不受限。
- [ ] **RB3-6 审计可追溯**：指标的创建/修改/删除审计记录的操作者是真实用户，不再是占位 `system`（现状缺陷，随 RB3-5 一并收口）。
- [ ] **RB3-7 目录可见**：角色管理页「埋点 / 元数据」下出现新增的「分析选择器 · 查看」一行，明细为完整句子；分析师档在该行打勾、在 `meta.view` 行不打勾；owner / 分析管理员两行都打勾；普通成员 / 外部人员两行都不打勾。
- [ ] **RB3-8 文案齐备**：新增文案在**全部已上线语言**（13 门）均存在，键集与占位符一致，切换语言后无源语言残留。
- [ ] **RB3-9 门禁**：`python3 scripts/arch_ratchet.py`、`python3 scripts/i18n_check.py`、`python3 scripts/i18n_scan.py --check`、后端 jest、前端 vitest、两端 `tsc` 全绿；棘轮若需上调（新增一条中文兜底文案），必须在提交说明写明原因。

## 4. 非目标

1. **不给分析师开放 Debug / 数据质量 / 对拍 / 数据表 / 接入指南**。本期是收回，不是放行；对拍属重查询（历史有 OOM 事故），保持管理员档。
2. **不修 Debug 的数据权限旁路**（§1 现象 2）。它是 v3.2 之前就存在的缺口，影响面为「被挂了数据权限策略的 owner / 分析管理员」；本期只在 `CODE_HANDOVER.md` 登记，不在本期实现。
3. **不做「我的角色与权限」自助页**。分析师仍看不到自己的权限列表（v2 PRD 未要求「项目权限管理」对该档开放）；是否给所有角色一个只读的自助入口，属产品决策，留待下一期。
4. **不改指标以外的资产写策略**。看板、卡片、分群、标签的锁定与编辑授权维持 v2 交付；分析主体与指标继续不走锁定。
5. **不改 member / external 档**。其他角色的验收由用户并行进行，本期不动其权限集合。
6. **不改数据模型**。无 Prisma schema 变更、无迁移、无 ClickHouse 变更。

## 5. 界面影响

| 界面 | 分析师 | owner / 分析管理员 |
|---|---|---|
| 埋点管理分组 | 不出现 | 不变 |
| 数据管理分组 | 仅「指标」（分组标题保留） | 不变（五项齐全） |
| 数据管理 → 指标页 | 可见可写（自己的） | 不变 |
| 数据管理 → Debug / 数据质量 / 数据表 / 接入指南 | 不可见，直链 403 | 不变 |
| 角色管理页 · 埋点/元数据 | 多一行「分析选择器 · 查看」 | 多一行，两行均打勾 |
| 指标详情抽屉 | 他人指标仍可打开查看（`metric.view` 不变），改/删时后端 403 并提示 | 不变 |

指标抽屉不在前端复刻归属规则（与分群/标签列表一致：按钮照常渲染，由服务端裁决并回可读提示）；该取舍记录在架构文档 §6。

## 6. 风险

- **选择器清单漂移**：以后有人给分析页加一个新的元数据读接口，忘了登记，分析师会再次 403。对策：清单在架构文档中显式列出，并约定「新增调用方须走同一清单登记」；后端单测锁定现有 8 条。
- **收口过猛**：分析师若在其它页面（如 AI 助手、看板卡片）间接依赖被收回的接口，会出现新的 403 反馈。对策：验收按 RB3-1 走全流程，覆盖分析、分群、标签、主体、指标五条路径。
- **棘轮上调**：新增一条中文兜底文案会让 `i18n_scan` 的 `modules/meta` 计数 +1，必须 `--force` 上调并记录原因；不允许顺手放宽其他目录。
- **角色管理页信息量**：目录新增一行后，owner 在「编辑分析管理员授权定义」时会看到该行，需确认勾选语义清楚（勾上 = 该角色可用选择器）。

---

## 7. 迁移与发布说明

- 无数据迁移。分析师在下一次登录后即可见变化：侧栏少两个分组的绝大部分入口，但分析能力不缺。
- 发布说明须写清：**分析师的埋点/数据管理入口收回到管理员档；分析页的事件、属性、维度选择器不受影响**。分析师若需要看元数据治理页，请管理员授予「分析管理员」或由 owner 调整。
- 若某项目此前自定义过「分析管理员」授权定义：该角色仍能照旧使用元数据选择器（走 `meta.view`），无需操作；如需在角色管理页把「分析选择器」也勾上，由 owner 重新保存一次该角色定义。
- 现网若已有分析师账号（邀请注册），无需任何操作。
