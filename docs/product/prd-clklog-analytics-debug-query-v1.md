# PRD：Debug 实时查询——口径修正 + 结果留档（v1）

> phase: `clklog-analytics-debug-query-v1`
> 状态：待评审（未实现）
> 问题来源：`docs/project/test-report-debug-query-2026-10-08.md`（D1–D4 均为生产实测）
> 相关既有文档：`docs/architecture/implementation-breakdown-clklog-analytics-v1.md`（P1-M7 Debug 实时查询）

## 1. 背景

Debug 实时查询（`/sa/meta/debug`）的定位是**埋点接入验证**：上报一条事件后，立刻按设备/账号/事件名看到 `sa_events` 里的原始行与完整 properties。2026-10-08 的生产实测确认功能链路是通的、结果与直查 ClickHouse 逐行一致，但有三个会直接影响使用者判断的缺陷，以及一条主要路径不可用：

| 编号 | 现象 | 影响 |
|---|---|---|
| D1 | 时间列比真实事件时间晚 8 小时 | 把「时间对不上」误导成 SDK / 时区问题 |
| D2 | 「共 N 条」其实是本次返回条数（命中 27492 显示「共 20 条」） | 误判上报量（多/少） |
| D3 | 按设备/账号查要 6–48 秒，账号维度 68.6 秒直接把前端 60s 超时打满 | 该页最常用的入口不可用 |
| D4 | `limit=abc` 返回 500 且回显 ClickHouse 内部报错 | 接口健壮性与信息外泄 |

同时，用户提出一项新能力：**Debug 查询要留下记录、永久保存、可被删除，方便回看当时的 debug 结果**。理由很实际——`sa_events` 只有 7 天窗口，今天的排查结论明天就查不到了；接入期常常是「同事 A 报的问题，同事 B 第二天要复看」。

## 2. 阶段目标与范围

**做**：

1. 修 D1（时间口径）、D2（计数口径）、D4（参数校验与错误外泄）；
2. D3 的可用性治理：查询窗口可选（默认收窄）+ 让时间条件能被索引/分区裁剪（后端 SQL 修正），并如实提示慢查询；
3. 新功能 F1：**Debug 查询留档**——每次查询自动生成一条记录（条件 + 命中数 + 结果行快照 + 操作人 + 时间），永久保存，可单条删除，可回看结果。

**不做（非目标）**：

- 不改 `sa_events` 的写入链路与社区版任何东西（红线 1、2）；
- 不做跨项目查看/共享（记录跟随项目隔离，与平台其它资产一致）；
- 不做导出（CSV/Excel）与记录对比/差异（列为后续可选）；
- 不做自动清理/TTL（「永久保存」是有意的产品选择；容量控制靠体积上限 + 人工删除）；
- 不把 Debug 查询改成异步任务队列（见 §6 风险 R2，列为后续 phase）。

## 3. 需求

### 3.1 D1 时间列必须显示真实事件时刻

判定口径（三选一不成立即不通过）：

1. 界面时间 = 事件真实发生时刻（在**查看者的显示时区**下渲染）；
2. 与「同一行的 ClickHouse `log_time` 值」相差为 0（不允许再出现恒定 ±8h）；
3. 实时流上做交叉验证：刚上报进库的行（`log_time` ≈ ClickHouse `now()`）在界面上显示为**当前时间附近**，不得显示成未来时间。

### 3.2 D2 条数必须区分「命中数」与「返回数」

- 列表区展示「命中 X 条」，其中 X 是**该条件下 7 天窗口内的真实命中总数**（与直查 `count()` 一致）；
- 同时说明「已显示最近 N 条」（N = 本次返回行数，受条数上限约束）；
- 空结果仍显示空态文案，不得显示「共 0 条」以外的误导信息。

### 3.3 D3 可用性

- 查询窗口可选：**近 1 小时 / 近 24 小时 / 近 7 天**，默认「近 24 小时」；
- 选「近 7 天」时给出成本提示（大数据量下设备/账号维度可能数十秒）；
- 查询中如实显示已等待时长；超过 10 秒显示「设备/账号维度较慢，建议同时填事件名」类提示；
- 服务端 SQL 必须让时间条件可被裁剪（详见实现方案 §1.3），**不得**为了变快而放宽或取消时间边界（红线 4）；
- **已知语义代价（须在界面说明条里写明）**：为可裁剪会补 `stat_date` 下界（±2 天余量）。`stat_date` 是「按项目时区切日」的列，
  因此**设备时钟偏差超过 2 天、或历史补数落进老分区**的行，不在本窗口过滤范围内——这类行在「事件分析 / 埋点管理」里仍可见，只是 Debug 页不列。

### 3.4 D4 参数校验

- `limit` 非法（非数字、0、负数、超大）一律按「无效参数」处理并返回 400，错误码稳定（`meta.debug.invalidLimit`），客户端拿得到可本地化的 messageKey；
- 任何 ClickHouse 报错不得原样出现在响应 message 中（服务端日志可留全文）。

### 3.5 F1 查询留档（新功能）

**触发**：用户在 Debug 页点「查询」并**成功返回**时自动留档一条。空结果也留档（「当天查了但当时没有数据」本身是排查信息）。失败（400/500/超时）不留档。

**一条记录包含**：

| 字段 | 说明 |
|---|---|
| 查询条件 | distinct_id / user_key / event（原样）、时间窗口、条数上限 |
| 结果概要 | 命中总数、返回行数、是否截断、耗时 |
| 结果行快照 | 返回的每一行：log_time（原文）、event、distinct_id、user_key、properties（原文） |
| 元信息 | 项目、操作人、查询时刻（平台时区展示） |

**留存与删除**：

- 永久保存，无 TTL；列表按时间倒序分页；
- 支持**单条删除**，删除需二次确认；删除写审计（谁、何时、删了哪条、该条条件与条数）；
- 删除只删这份快照，**不动** `sa_events` 任何数据。

**权限**（待确认，见 §6 R3）：

- 查看：`meta.view`（且限本项目）；
- 删除：创建者本人 + 平台超管 + 持有 `meta.edit` 的项目成员，三者之一。

**体积与诚实性**：

- 单条最多保存本次返回的行数（≤100 行）；
- 单行 properties 原文超过上限（32KB）时截断并在界面标注「已截断」；
- 单条记录总量超过上限（1MB）时按行丢弃剩余行并标注 `truncated`，同时在界面明示「本次记录不完整」——不允许静默截断。
  （两个上限必须同量级：8KB × 100 行 = 800KB 会让 1MB 这条永不生效，故单行取 32KB。）

**回看**：历史列表 → 点开某条 → 看到与当时一致的表格（只读），含条件、命中数、操作人、时间；表格时间列与 §3.1 同口径。

### 3.6 F2 项目级留档开关（默认开）

- 开关粒度：**项目级**，默认 **开**；
- 关闭时：查询照常可用，但**不落档**，界面明示「本项目已关闭留档，本次结果不会保存」（不许静默跳过）；
- 已存在的历史记录不受开关影响，仍可查看与删除；
- 可关闭的身份：与项目时区设置同一权限（运维/超管，`ops.owner.assign`）；
- 入口：Debug 页历史区域内的开关（对该权限可见），避免另起一页。

## 4. 界面结构（文字线框）

```
┌ Debug 实时查询 ──────────────────────────────────────────┐
│ ⓘ 说明条（含新窗口口径：默认近 24 小时）                    │
│ [distinct_id] [user_key] [事件名] [窗口▾] [条数] [查询]     │
│ 错误/提示条（慢查询提示、未留档提示）                        │
│ ── 本次结果 ──                                            │
│ 命中 27,492 条，已显示最近 20 条（共 20 行）    [已留档 #..] │
│ 表格（时间 / 事件 / distinct_id / user_key / properties）  │
│ ── 历史记录 ──（默认折叠或下方 Tab）                        │
│ 时间 | 条件摘要 | 命中 / 返回 | 操作人 | 操作(查看/删除)     │
└──────────────────────────────────────────────────────────┘
```

## 5. 验收标准

| 编号 | 判据 |
|---|---|
| AC-1（D1） | 用一条已知行对拍：界面显示时间与 ClickHouse `log_time` 在同一时区口径下相等；实时流交叉验证不出现「未来时间」 |
| AC-2（D2） | `distinct_id=样例标识`（生产 27492 命中）界面显示「命中 27492 条，已显示最近 20 条」 |
| AC-3（D3） | 默认「近 24 小时」窗口下按设备查询在生产数据量级上 <3 秒返回；「近 7 天」可选且有成本提示；SQL 仍带时间边界与 `project_name` 过滤 |
| AC-4（D4） | `limit=abc` → 400 + 稳定错误码；响应体中不含 ClickHouse 原文；`limit=0/-5/1000` 行为与现状一致（1 / 1 / 100） |
| AC-5（F1-留档） | 查询成功 → 历史列表出现一条；刷新/重登/换浏览器仍在；重启服务仍在（落库而非内存） |
| AC-6（F1-回看） | 打开历史记录看到与当时一致的行（含 properties 原文）与命中数；时间列与 AC-1 同口径 |
| AC-7（F1-删除） | 单条删除后列表消失、直连接口 404；审计表出现删除记录；`sa_events` 行数不变 |
| AC-8（F1-截断） | 构造超限 properties 的行：界面标注「已截断」且记录标记 `truncated=true`，不静默截断 |
| AC-9（F1-权限） | 非本项目成员看不到该项目记录；无删除权限者删除被拒（403） |
| AC-10（门禁） | `arch_ratchet`、`i18n_check`（13 语言键集一致）、`i18n_scan --check` 全绿；新增文案无硬编码 |
| AC-11（裁剪代价可见） | 页面说明条写明 `stat_date` 裁剪口径与 ±2 天余量；构造一条 `stat_date` 偏差 >2 天的行，确认其不出现且界面口径与文档一致（如实，不静默） |
| AC-12（F2 开关） | 关闭本项目留档后：查询成功但历史列表不新增，界面出现「已关闭留档」明示；开回后恢复落档；已有记录在关闭期间仍可查看/删除 |

## 6. 风险与开放问题（决议已定，2026-10-08）

| 编号 | 事项 | 决议 |
|---|---|---|
| R1 | **隐私**：记录会**永久**保存原始 `properties`（可能含设备/账号标识与业务参数），比 `sa_events` 的 7 天窗口留存更久 | **已决：加项目级开关，默认开**（F2）；配合按项目隔离 + 权限 + 可删除 + 删除审计 |
| R2 | D3 的彻底解法（跳数索引 / 异步任务） | **已决：本 phase 不做**，先用「窗口可选 + `stat_date` 裁剪」；索引与异步登记为后续 phase 候选（索引需先在 staging 演练，红线 6） |
| R3 | 删除权限面 | **已决**：创建者本人 / 平台超管 / 持 `meta.edit` 的项目成员，三者之一可删 |
| R4 | 记录量增长（永久保存） | 单条 ≤1MB、单条 ≤100 行；列表分页；后续可按项目加总量视图 |
| R5 | 窗口默认从「固定 7 天」改为「默认 24 小时」 | **已决：改**（1h/24h/7d，默认 24h）；需同步更新既有说明文案与 `implementation-breakdown` 描述 |
