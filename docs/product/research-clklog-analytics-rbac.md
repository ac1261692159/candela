## 1. 它是什么

分析平台的权限不是「登录了就能进」。要同时回答四件事：

| 问题 | 名称 | 例子 |
|------|------|------|
| 这个人是谁 | 身份 | 用户名密码、token |
| 他属于哪个项目 | 成员 | 用户 A 是 `clklogapp` 的分析师 |
| 他能点哪些功能 | 功能权限 | 能否进埋点管理、能否保存卡片 |
| 他能看见哪些行/列 | 数据权限 | 只能看 `channel=app` 的事件；看不见手机号属性 |

后两件经常被揉成一个「角色」字段。神策/数数把它们拆开：**角色管功能，数据权限管可见数据**。成员组则是「一批人共用同一套角色 + 数据权限」。

和现有「用户分群」不是一回事：分群圈的是**分析主体 ID**（终端用户）；这里管的是**平台登录者**。

## 2. 主流模型（该用哪一层）

分析 SaaS 几乎都是「分层 RBAC + 轻量数据范围」，不是纯 ABAC，也不是 Zanzibar 级 ReBAC。

### 2.1 RBAC（角色 → 权限包）

NIST RBAC：用户绑定角色，角色绑定权限。优点是可解释——角色管理页能列出「这个角色到底能干什么」。神策的三列表（功能 / 操作权限 / 功能明细）就是 RBAC 目录的产品化。

缺点：角色是功能开关，回答不了「同是分析师，只能看华东数据」。

### 2.2 ABAC（属性策略）

按主体/资源/环境属性写策略（部门、国家、数据分级）。灵活，但策略不可读，分析师看不懂自己为什么查不到数。适合作为**数据权限**的实现，不适合作为唯一模型。

### 2.3 ReBAC / Zanzibar（关系）

「用户 U 对看板 D 是 editor」。看板分享、协作空间走这层。神策的「设置看板共享与协作」「空间成员」是 ReBAC 味道。我们 P1 把资产 `owner` 写成「只能看自己的」，等于退化成私有云盘，和神策项目空间相反。

### 2.4 分析产品的通行分层

| 层 | 谁在用 | 管什么 |
|----|--------|--------|
| 平台 / 组织 | 神策超管、GitLab Owner、Grafana Org Admin | 建项目、指定项目 owner、运维、全局用户 |
| 项目 / 空间 | 神策项目角色、Mixpanel project role、Amplitude project | 本项目功能与成员 |
| 数据范围 | 神策数据权限、Mixpanel data views、Amplitude user-property filters | 事件/属性/行过滤 |
| 资产分享 | 神策看板共享、Grafana folder perms | 某块看板对谁可见 |

结论：**功能用 RBAC（预置角色 + 权限目录），项目用成员关系，数据用 ABAC-lite（事件/属性白名单 + 用户属性过滤），看板可见性以后再加分享。** 不要把平台超管做成项目角色之一。

### 2.5 各家对照（功能层）

| 产品 | 平台角色 | 项目预置角色 | 自定义角色 | 数据权限 | 成员组 |
|------|----------|--------------|------------|----------|--------|
| 神策 | 超管（系统管理-项目接入） | owner / 分析管理员 / 分析师 / 普通成员 / 外部人员 | 有 | 有（与角色分开） | 有 |
| 数数 | 超管 | 项目 owner / 管理员 / 分析师 / 普通成员 等 | 有 | 有 | 有 |
| Mixpanel | Org | Admin / Analyst / Consumer | 弱 | Data views | 弱 |
| Amplitude | Org Admin | Admin / Manager / Analyst / Viewer | 有 | 用户属性限制 | 有 |
| Grafana | Org Admin | Admin / Editor / Viewer | 无（靠 folder） | 无行级 | Team |
| GitLab | Instance Admin | Owner / Maintainer / Developer / Guest | 自定义角色（新） | 仓库级 | Group |

私有化分析平台和神策最像：一个部署多个项目、项目内职能角色固定、超管管运维。Mixpanel 的 Consumer ≈ 我们的普通成员；Grafana Viewer 只有看板、没有 Explore，对应「普通成员只看看板」。

## 3. 神策怎么拆（截图 + 权限表）

### 3.1 信息架构

截图（角色管理）是三栏管理台，不是一张开关矩阵：

1. **项目管理侧栏**：项目配置、成员管理、角色管理（当前）、数据权限、公开链接管理。角色和数据权限是并列入口。
2. **角色列表**：`+ 自定义角色`、搜索、预置角色清单。选中项右侧蓝条。
3. **主区**：角色名 +「预置角色」标签；约束用蓝 info 条写死（「项目最多 1 位 owner，仅超管在系统管理-项目接入中设置」）；下面一张表：**功能 / 操作权限 / 功能明细**。明细是给人读的句子，不是权限码。

要点：权限必须**写清楚**。只给一个「分析师」徽章、不展示明细，不算做成了角色管理。

### 3.2 两顶帽子

| 帽子 | 谁授予 | 范围 |
|------|--------|------|
| 超管 | 系统 | 运维、项目接入、指定项目 owner |
| 项目角色 | 项目内 | 本项目功能；**不含运维** |

项目 owner 不是超管。超管可以同时当某个项目的 owner（两顶帽子戴在同一个人头上）。每个项目 **恰好 1 个** owner。

### 3.3 预置角色的职能差（压缩）

完整表见 gap §11。按「能做什么」压缩：

| 角色 | 一句话 | 相对上一档少什么 |
|------|--------|------------------|
| 项目 owner | 项目空间内除运维外全部 | 没有超管运维；owner 席位只有超管能指定 |
| 分析管理员 | 几乎等同项目管理员 | 无资产中心/资产箱；不能改他人分群标签；不能看项目内**全部**私有看板；不能改 owner。**能**管成员与权限 |
| 分析师 | 查询 + 存卡片 + 编看板 + 部分用户资产 | 无埋点方案/验收/Debug 编辑；无项目配置与成员管理；元数据只能改显示名/虚拟对象，不能管上报黑名单 |
| 普通成员 | 看看板、临时改筛选、导出 PDF、探索 | 无分析模型、无用户、无元数据 |
| 外部人员 | 看已分享看板、导出 | 不能改筛选；几乎无模型（仅下载导出） |

神策把「项目管理员」和「分析管理员」做成同一档职能：配置项目、管成员、管埋点、管分析。没有单独的「项目管理员」角色。

### 3.4 成员与成员组

成员 = 登录用户在本项目的一条关系：角色 + 可选数据权限。

成员组 = 命名的人集合，组绑定角色和数据权限，组内成员继承。一个人可以既有直接角色又在多个组里。通行合并规则：

- **功能权限**：取并集（最宽角色生效）。owner 席位不能通过组获得。
- **数据权限**：取交集（更严的过滤生效）。

### 3.5 数据权限（与角色并列）

神策数据权限不是角色表里的一行，而是给成员/组挂策略，常见三维：

1. 可见事件
2. 可见事件属性 / 用户属性
3. 行过滤（用户属性条件，例如只要 `channel=app`）

查询（含看板刷新）按**查看者**的数据权限收窄，不是按看板创建者。否则数据权限形同虚设。

owner / 超管通常不受数据权限限制。

## 4. 我们现在有什么

P1（`phase: clklog-analytics-user-rbac`）已落地：

- `SaUser` + 登录 token；全局字段 `role = admin | analyst | viewer`
- 资产 `owner` = 用户 id；非 admin 只能看自己的看板/卡片
- 前端：未登录跳登录；菜单里 API Key / AI Workspace 仅 `role===admin`
- 项目是请求头里的 `project_name`，前端写死可选 `clklogapp` / `default`，**没有项目成员表**
- 生产上实际只有 **admin 用户**

这套解决了「谁都能访问」，但和神策不是同一类产品：

| | P1 | 神策式 |
|--|----|--------|
| 角色挂在哪 | 用户全身一份 | 平台帽子 + 每个项目一份 |
| admin | 全局上帝 + 看全部资产 | 运维超管；项目内另当 owner 才有项目权 |
| 分析师 | 只能看自己的看板 | 项目内按角色与分享看 |
| viewer | 只读自己的资产 | 普通成员看分享的看板 |
| 成员组 | 文档写了 P2，未做 | 一等概念 |
| 数据权限 | 无；v1 架构写明「不实现行列级」 | 与角色并列 |
| 权限说明 UI | 无 | 三列表，预置角色只读展示 |

P1 的 `admin` 现在同时干了超管和项目 owner 两件事。继续加角色到 `SaUser.role` 会把运维和分析空间焊死。

现网功能面（用来裁权限目录，不抄神策没有的模块）：

| 我们已有 | 对应神策功能组 |
|----------|----------------|
| 看板 / 卡片 / SQL 卡 | 看板使用、模型使用（部分） |
| 事件 / 漏斗 / 留存 / SQL | 模型使用 |
| 用户分群 / 标签 / 分析主体 | 用户分群、用户标签、项目配置-分析主体 |
| 元事件 / 属性 / 虚拟事件属性 / Debug / 数据质量 / 指标 | 元数据管理、埋点管理、指标管理 |
| API Key、AI Workspace | 运维（我们自己的，神策表里没有） |
| 无 | 资产中心、项目接入、时区、资产箱、数据集成、预警、探索、模板中心、汇率、公开链接、多语言、用户细查 |

## 5. 差在哪（决策输入）

1. **缺项目空间成员关系**。现在换项目名就能进另一个项目的数据（只要知道名字）。
2. **缺权限目录与说明页**。角色不可解释，也无法对标神策截图。
3. **缺数据权限**。私有化多业务线共用一个项目时，外部人员和运营不能看全量事件。
4. **资产默认私有** 和「项目成员看看板」冲突。普通成员在 P1 下看不到别人的看板，产品目标却是「只看看板」。
5. **神策有、我们无的功能组**不要做进本期权限开关（开关永远关着等于噪音）。目录只收已有能力 + 已确定要做的运维占位；其余记 gap。

## 6. 推荐（给我们自己的模型）

采用 **平台超管 × 项目 RBAC × 数据权限策略 × 成员组**。细则进 PRD，这里只锁模型：

1. **超级管理员是平台帽子，不是项目角色。** 拥有运维权限（现有 API Key / AI Workspace，以及后续系统内运维管理）。超管在系统侧指定每个项目的唯一 owner；超管自己也可以是某项目 owner。
2. **项目预置五角色**：项目 owner、分析管理员、分析师、普通成员、外部人员。不单列「项目管理员」——与神策一样，分析管理员 = 项目空间管理员。
3. **项目 owner**：除运维外的全部项目空间权限；每项目 1 人；只由超管指定。
4. **分析管理员**：功能上与 owner 对齐（含埋点、成员、配置）；可以添加/删除管理员；**不能**指定/替换 owner；**不能**改「分析管理员」角色本身的权限定义——只有 owner 能改管理员角色的授权。
5. **分析师**：全部查询、保存卡片、编辑看板、用户（分群/标签等）；**无埋点管理**。
6. **普通成员**：只看看板。
7. **外部人员**：按神策收窄（看已分享看板、导出）。
8. **成员组**：项目内命名集合，绑定非 owner 角色 + 数据权限；功能取并、数据取交；组不能产生 owner。
9. **数据权限**：事件可见、属性可见、可选用户属性行过滤；挂到成员或组；查询按查看者收窄。owner 与超管不受限。
10. **角色管理 UI 必须是神策那张说明表**，预置角色默认只读展示。自定义角色本期不做。
11. **看板用最多两层文件夹管理**；锁定与点名编辑授权互斥，写路径一张 AssetPolicy 表判定。卡片不进文件夹。分析主体/指标不锁定。

不采用：把超管做成第六个项目角色；纯 ABAC 无角色；继续把 `SaUser.role` 当全局身份；锁和授权同时亮在同一对象上。
