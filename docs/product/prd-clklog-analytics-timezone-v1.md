## 1. 阶段目标与范围

现状把 `Asia/Shanghai` 当全平台唯一日历：时间窗、粒度桶、告警窗口、落库写串、前端展示各自引用，共 6+ 处硬编码与一批「依赖进程时区恰好正确」的隐式假设（调研 §4/§5）。这带来两类后果：海外/多时区使用者看到的「今天」不一定对；实例迁机、宿主改时区、浏览器跨时区任一事件都可能静默改口径（已有 ZQ-2 分群日更窗错位为现役缺陷，AL-01 为已发生的事故形态）。

本期把时区从「散落的字面量」升级为**一层系统能力**：

| 模块 | 本次做什么 |
|------|------------|
| 平台时区 | 实例级单点配置（默认 `Asia/Shanghai`），后端单点读取、前端随用户信息下发；改配置即换全平台默认日历 |
| 查询口径时区 | DSL `time_range` 增加可选 `timezone`（IANA 名）；事件/漏斗/留存/自定义 SQL/指标在同一时区解析「今天」、切粒度桶、过滤时间窗；时间面板可临时切换查看时区 |
| 卡片与看板 | `timezone` 随卡片 DSL 持久化；看板刷新沿用卡片时区；无 `timezone` 的旧卡片 = 平台时区（行为与今天逐字节一致） |
| 展示贯通 | 查询结果时间列/图表轴/表格按展示时区渲染，不再随浏览器时区漂移 |
| 结构清偿 | 调研 ZQ-1～ZQ-6 清零：写串进程时区固化、分群/标签/数据管理/告警「今天」口径统一、cron 显式时区、周粒度统一周一、静默时间契约固化、上海字面量收敛单点 |

**默认零变化**：平台时区默认 `Asia/Shanghai`、所有时区字段缺省 = 平台时区。本期交付后，不配置任何新东西的用户与既有卡片看到的行为与上线前完全一致。

## 2. 时区模型（口径定义）

1. **平台时区（platform timezone）**：实例级统计日历，IANA 名（如 `Asia/Shanghai`），默认 `Asia/Shanghai`。事件落库 `stat_date`（既有数据与新增数据）永远按平台时区解释；历史 `sa_events.stat_date` 列已按上海落地，平台时区改成非上海需要**同时**意识到历史分区口径不追溯（见 §5 非目标）。
2. **展示/查询时区（display timezone）**：一次查询所用的日历。缺省 = 平台时区；可在时间面板临时切换，或随卡片 DSL 持久化。它决定：「今天」的锚日、`start/end` 起止日的边、粒度桶切分、前端时间渲染。
3. **换算口径**：事件时间是 epoch 毫秒绝对时刻。展示时间 = 该时刻在展示时区的日历表达；统计 = 按展示时区切日/周/月后聚合。**不存在逐事件偏移属性**（epoch 模型不需要；调研 §6.3）。
4. **周/月口径**：周一起点（与 time-range-v1 PRD 一致）；月按自然月。夏令时由 IANA 规则自动正确（L2 对固定偏移方案的结构性优势，调研 §6.1-7）。
5. **与时区无关的面**：上报 `time` epoch 毫秒不变；Ch 服务端时区、容器 `TZ`、Grafana、cron 物理触发时刻的管理（非业务口径面）不在用户可感知范围。

## 3. 用户流程

1. **默认使用**：用户什么都不配。所有「过去 7 天」「今天」、粒度桶、展示时间与今天完全一致（平台时区 = Asia/Shanghai）。
2. **切换查看时区**：在任意分析页/自定义 SQL 的时间面板底部选时区（搜索 IANA 名，如 `America/New_York`，显示当前偏移 `UTC-4`）。应用后用该时区重新解析「今天/过去 N 天」、切桶、渲染结果。URL/表单状态随行，刷新不丢。
3. **保存卡片**：卡片区 DSL 记入 `time_range.timezone`；加入看板后，看板刷新按卡片自己的时区解析动态窗与切桶。不同卡片可在同一看板使用不同时区。
4. **管理面**：告警/埋点/运维等管理页的时间戳统一按平台时区渲染（不再是 UTC 墙钟截断或浏览器时区二义）。
5. **运维配置平台时区**（少见动作）：实例管理员改应用配置 `timezone` 并重启服务；新查询与落库立即按新平台时区。文档明确：历史 `stat_date` 分区口径不追溯，平台时区是**部署期决定**，不是日常开关。

## 4. 验收标准

- [ ] **SC-1 单点**：业务代码内 `Asia/Shanghai` 字面量仅存在于默认常量单点（后端）与前端同构默认常量；其余全部经单点服务读取（`rg` 清单前后对比为证）。
- [ ] **SC-2 进程时区无关**：在 `TZ=UTC` 与 `TZ=Pacific/Auckland`（UTC+12/+13）下后端单测全绿；ingestor 以 `TZ=UTC` 运行时，写入的 `log_time/stat_date` 与显式平台时区日历逐行一致。
- [ ] **SC-3 口径清零**：ZQ-1～ZQ-6 逐项关闭——分群/标签 computeDay、数据管理保护月、质量对拍默认日、告警 fired_today 全部按平台日历；cron 三任务显式声明时区；自定义 SQL 周粒度与事件分析同为周一；静默时间只接受 ISO 8601（带偏移），非法格式 400（错误码契约）。
- [ ] **SC-4 平台时区可配置**：把平台时区改为 `America/New_York` 后，时间窗默认「过去 7 天」、粒度桶、前端展示、告警通知时间全部按纽约日历（本地集成测试或测试环境实测）。
- [ ] **SC-5 查询口径时区化**：同一查询在 `Asia/Shanghai` / `UTC` / `America/New_York` 三种 `timezone` 下，时间窗边界与分桶与手算逐行一致（CH 实测矩阵，覆盖日界两侧各 ±1 小时事件）；含时/日/周/月粒度。
- [ ] **SC-6 零变化兼容**：不带 `timezone` 的请求/旧卡片结果与改造前**逐字节一致**（同一 SQL、同一结果集对拍）；看板既有卡片刷新行为不变。
- [ ] **SC-7 展示贯通**：浏览器系统时区改成 `Pacific/Honolulu`（UTC-10）后，查询结果时间列与图表轴仍按展示时区渲染（与查询口径一致），告警列表等管理面按平台时区渲染，不再出现 UTC 墙钟截断。
- [ ] **SC-8 门禁**：相关单测与 `python3 scripts/arch_ratchet.py` 通过；前端 i18n 校验不受影响。

## 5. 非目标

1. **不做用户级时区偏好**（`SaUser.timezone`、Profile 设置项、登录下发）——属 i18n 设计 §13.1 登记的后续 phase，依赖本期贯通。
2. **不做通知按收件人时区**：告警窗口与通知时间统一按平台时区；「按收件人时区」与用户偏好一起做（同「按收件人语言」模式）。
3. **不做项目级时区**（`SaProject.timezone` 与 RBAC 项目设置）——需求出现时单独立项；本期平台时区是实例级唯一默认。
4. **不做逐事件时区偏移 / 多时区结算**（数数 `#zone_offset` 模式）：epoch 事件时间模型用不到；客户端时钟漂移治理（未来时间校验、偏差告警）另行立项（调研 ZQ-8-⑤）。
5. **不改历史数据与 DDL**：不 ALTER `sa_events`、不重算历史 `stat_date`、不动社区版 19 张聚合表与官方镜像（红线 1）；CH 服务端 `<timezone>` 不设，容器 `TZ` 参数维持现值。
6. **不改时间粒度集合与窗口上限**（分钟粒度 1 天上限、SQL 90 天上限沿用）；不做 VS/上期对比；不做「按时段（0-23 时）」筛选这一缺口（gap §2.6，另行登记）。
7. **不动 Grafana 与社区版组件显示时区**（ZQ-8-⑥ 仅登记）。
8. **埋点 SDK 不新增字段**：`$timezone_offset` 继续只进 properties JSON 不消费。

## 6. 兼容与迁移

- **DSL 加法式**：`time_range.timezone` 为可选字段；旧卡片、旧调用方、Harness 快照里的 DSL 无此字段 → 平台时区，行为同今。
- **API 出参加法式**：`applied_time_range`（SQL 执行回显）扩展返回 `timezone`；`/auth/me`（或登录响应）增加 `platform_timezone` 供前端初始化。
- **错误契约**：非法 `timezone` 走既有错误码机制（`messageKey`），400。
- **口径修正声明**（ZQ-2/ZQ-3/ZQ-6 属「修错即改口径」，上线说明须显式声明）：
  - 分群/标签日更窗从「UTC 今天」改为「平台日历今天」——首日重算一次，UTC+8 下窗口前移 8 小时，属修错；
  - 自定义 SQL 周粒度从「周日始」改为「周一始」——与 PRD（time-range-v1「周一=周首」）对齐，历史卡片下周起的周桶标签可能平移一天；
  - 数据管理「当月保护」从 UTC 月改为平台月——每月首末 8 小时的保护判断回到正确侧。
