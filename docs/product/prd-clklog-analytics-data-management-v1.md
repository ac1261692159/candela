## 1. 背景

运维面板首期（`clklog-analytics-ops-console-v1`）把「看见自己」做实了：慢 SQL、服务器状态、磁盘用量预估。看得见之后立刻暴露下一个问题——**看得见，但没有处置手段**。

2026-09-07 实测事实：

| 事实 | 影响 |
|---|---|
| `/data` 已用 50% 且增长快，`receiver` 原始报文日志 1.3T | 无清理入口，按当时增速预计数月内写满，连坐 ClickHouse |
| `clklog_sa.sa_events` 亿级行、`clklog.log_analysis` 双份存储 | 分析主数据与社区版数据各占一份，重查询即全局事故（CH 容器 memcg 12GiB，对拍两次打挂过 CH） |
| 社区版 `log_analysis` 无 project 隔离、无 TTL | 社区版不允许侵入改造（红线 1），只能在分析平台侧提供治理视图与生命周期设置 |

目标一句话：**在单机小内存 ClickHouse 的约束下，把数据生命周期治理收进运维面板——能盘、能预演、能安全地清，且每个动作可追溯。**

## 2. 用户与权限

| 项 | 规则 |
|---|---|
| 可见人群 | 仅平台超管（`platform_role = super_admin`） |
| 菜单 | 运维 → 数据运维（`/ops/data-management`），与 慢 SQL / 服务器状态 / 监控告警 同级 |
| 接口 | `isAdmin()` 身份兜底 + 权限码；非超管 403 |
| 边界 | 治理的是平台存储本身，与项目数据权限无关（超管无需是项目成员） |

## 3. 范围（已交付）

### 3.1 存储概览（只读）

- 盘点 `clklog_sa` 与 `clklog` 两库各表：行数、压缩后字节、分区数、最近写入时间（`system.parts` 按 active 聚合）。
- 顶部汇总：盘点表数 / 总行数 / 压缩后总量。
- **按时间趋势**：小时级采样（复用磁盘采样的同表 `hostmetricsample`，`metric_key = table:{db}.{tbl}:rows|bytes`），支持近 7 / 30 / 90 天切换。
- 列表支持排序与分页，表名可定位到清理预演。

### 3.2 数据健康（只读，对拍结论聚合）

- 展示最近一次对拍快照：对拍时间、范围、状态、告警天数、CRC 重复行（近似值）。
- 提供跳转「数据质量」页的入口。
- **不迁移**数据质量页：对拍属「数据正确性」，数据管理属「数据生命周期」，语义不同，页面留在元数据菜单原位。

### 3.3 清理预演（只读，dry-run）

- 选定 表 + 保留天数 → 返回将被影响的**分区清单**、行数、字节数、释放空间预估。
- 预演查询强制护栏：时间下界、`max_memory_usage=4GB`、`max_threads=2`、600s 上限（对拍事故直接教训）。
- 候选过滤：仅允许**过去月份**的 `YYYYMM` 分区；当前月、未来分区、非 `YYYYMM` 命名一律拒绝。

### 3.4 TTL 设置（动作类）

- 对日志类表设置 `ALTER TABLE ... MODIFY TTL <time_col> + INTERVAL N DAY`，一次性 DDL，后台渐进生效，可回退（改天数即可）。
- 时间列按表白名单映射，天数有上下界校验。
- 定位为**首选清理手段**：代价低、可回退。

### 3.5 分区清理执行（动作类）

- 流程：预演 → 展示影响面 → **输入表名二次确认** → 执行 `DROP PARTITION`（月粒度，秒级元数据操作，**不可恢复**）。
- 执行后轮询 `system.mutations` 展示进度；未完成前不允许发起新的清理（IO 保护）。
- 定位为**次选手段**：仅用于大批量历史数据下线。

### 3.6 日志目录治理（动作类，服务器状态页）

- 对白名单目录（种子：receiver 原始报文日志，保留 3 天）按 mtime 清理 `*.log`：递归限深 3，只碰 `.log`，绝不触碰 ClickHouse / MySQL 数据目录。
- 保留天数可配、自动清理开关、立即清理带预演确认。
- 程序内定时执行（每小时），不依赖 cron / Puppet。

### 3.7 动作审计（只读）

- 每次写动作（自动 + 手动）写 `ops_action_log`：who / when / what（表或目录）、`dry_run_snapshot`（执行前快照）、结果与错误。
- 页面展示最近动作，可按表筛选。

> **验收记录（2026-09-15，生产 17175）**：见 `docs/project/acceptance-clklog-analytics-data-management-v1.md`。实测发现并修复 **6 处**：TTL 设置因 CH 语法错误完全不可用、TTL 解析缺失、护栏错误返回 500、按日分区表预演无说明、**TTL 触发全表 part 重写（改为 `materialize_ttl_after_modify=0` 纯元数据操作后，亿级行表实测 0.11s 返回）**、长 DDL 导致审计丢失（改为「先落 running 再执行」）。真实分区的 DROP 未执行，需授权。

## 5. 非目标

1. **不做**社区版表结构改造（红线 1）：治理手段只走 TTL / DROP PARTITION / 目录级日志清理。
2. **不做** `ALTER DELETE` 定点脏数据清理（未来时间戳数据专项，需先确认设备时钟错乱范围）。
3. **不自动清理** `sa_events`（分析主数据），V1 只盘点不默认清理；是否下线历史需产品确认。
4. **不做**多节点 / 分布式存储视图（当前单节点部署）。
5. **不引入** Prometheus / Grafana 或外部存储监控栈。
6. **不迁移**数据质量（对拍）页面，只做结论聚合与入口。
7. **不做**清理动作的定时排程（TTL 自身即渐进生效；分区清理保持人工触发 + 审计）。

## 6. 关键产品决策

| 决策 | 选择 | 理由 |
|---|---|---|
| D1 | 清理分级：TTL 首选、DROP PARTITION 次选、ALTER DELETE 暂不做 | 按「可回退性 / 代价 / 风险」排序，先给低风险手段 |
| D2 | 动作一律「预演 → 人工二次确认 → 审计」 | 面板自身不能成为故障源；不可恢复动作必须留痕 |
| D3 | 对 sa_events 只盘点不默认清理 | 它是分析主数据，误删等于毁掉分析能力 |
| D4 | 对拍页不迁移，只聚合结论 | 语义不同（正确性 vs 生命周期）；迁移会破坏既有书签与习惯 |
| D5 | 日志目录治理做进程序内，不依赖 cron/Puppet | 治理闭环在应用侧，Puppet 只存配置模板（红线 7） |
