## 1. 它是什么

用户分群 = **预先圈出一批分析主体 ID**，之后在分析（筛选/分组）和运营里当「属于 / 不属于」用。

和两件现有能力不是一回事：

| | 留存里的 cohort | 用户分群 |
|--|------------------|----------|
| 含义 | 按日期切的队列 | 命名的用户集合 |
| 是否资产 | 查询结果，不入库 | 项目资产，可复用 |

和 **用户标签** 也不同：标签给每个人打值（可多值、可分层）；分群只回答「在不在这群里」。数数建议一个分群只服务一个场景。

核心产品决策：**预计算，不是每次分析即席圈人。** 分析用的是上次算好的成员表，换时效换性能。日更通常够分析；运营要更新。

---

## 2. 两种定义方式

| 方式 | 存什么 | 人数会不会变 | 数数类型 | 神策类型 |
|------|--------|--------------|----------|----------|
| **ID 集合型** | 成员 ID 快照 | 几乎不变（除非再导入） | ID 分群、**结果分群** | 导入创建、结果保存 |
| **数据条件型** | 规则；每次按当前数据重算 | 会变 | 条件分群、SQL 分群 | 规则创建 |

创建入口不一样：

- 条件 / ID / SQL：用户分群页「新建」，选类型卡。
- **结果分群不在这三张卡里**：在分析表「人数」下钻处保存当前结果集。截图里的创建页因此只有三张卡，并不代表没有结果分群。

默认上限（数数手册，可调）：条件+SQL 项目约 200；ID / 结果每人约 50。

## 3. 数数前端（截图）

### 3.1 列表

列可搜、可显隐、可拖排序。锁死不可藏、不可挪：**分群名、显示名、操作**。其余可选：

分析主体、分群类型、创建人、**实时的使用状态**、**计算方式**、最后计算时间、人数、备注。

「人数」是该分析主体的去重人数，不是事件次数。「实时的使用状态」表示是否被运营/实时任务占用，不是计算是否成功。

### 3.2 条件分群

单页三段，左侧锚点：分群规则 → 计算设置 → 基本信息。

1. **分析主体**：默认预置「用户」；下拉里可「管理分析主体」。
2. **分群条件**（这就是条件配置器，不是另有一张复杂表单）：一条条件是一句可读的话。
   已拍到的默认句：`做过` + 事件 + `的次数` + `大于` + `0` + `在过去7天`。
   「+ 添加分群条件」只有三种：做过/没做过事件、依次/没依次做过事件、用户属性满足。
   多条靠继续添加；截图未展示条与条之间的且/或，也未展开「次数」改成别的量、事件上再筛属性、依次做过的步骤编辑器。
3. **定时计算**：开关。关 = 只算一次（再手动刷新）；开 = 每日按规则重算。列表「计算方式」为「手动」即关定时。
4. **显示名 / 分群名 / 备注**：打开页就用时间戳占位（`分群20260905_114337` / `cohort_20260905_114337`）。分群名是标识，显示名给人看。

SQL 分群不是条件配置器：同一套左侧步骤，中间是 SQL 编辑器 + `${PartDate:date1}` 时间参数，结果只要主体 ID 一列。

分析主体若来自**事件属性**，条件分群不能用「未做过 / 未依次做过」（没发生过该属性值的人无法从事件表圈出）。

### 3.3 ID 分群

左侧只有「分群规则 / 基本信息」，**没有定时计算**。UTF-8 CSV，可下载模板，可多次上传覆盖。关联字段通常是账户 ID、访客 ID，或文本/数值用户属性。对不上的行丢弃。更新方式 = 再传文件。

### 3.4 SQL 分群

规则 + 计算设置 + 基本信息。结果 **只要分析主体 ID 一列**。编辑器可插入时间参数（按更新日滚动窗口）、试跑。右侧数据字典：表字段（截图为 `v_event_1` 事件表、`v_user_1` 用户表）和事件属性。定时计算开关与条件分群相同。

### 3.5 分析主体（分群的前置）

独立管理页：预置「用户」；可新建，**主体来源**绑一个属性（截图选「账户 ID」`#account_id`），再起主体名称。列表可调顺序。属性选择器：搜、全部/事件属性/用户属性、收藏、认证、显示名+内部名+类型。

没有多分析主体，分群的「人数」和分析筛选的去重口径对不齐。

### 3.6 使用与刷新（手册，截图未拍）

| 动作 | 条件 / SQL | ID | 结果 |
|------|:----------:|:--:|:----:|
| 创建后立刻算一次 | 是 | 是 | 是 |
| 每日定时 | 可开 | 否 | 否 |
| 手动刷新 | 是 | 再上传 | 否 |
| 点人数看用户列表 | 是（表最多约 1000 行，下载上限约 50 万） | 是 | 是 |
| 分析里当筛选/分组 | 是 | 是 | 是（选择器里往往排在条件/ID 后面） |

分析里用的是**预计算结果**，看板换时区不会重算这群人。

删改时若被报表/预警占用会提示影响面。

## 4. 神策对照

分析产品（未上「用户画像」套件）三种创建：

1. **规则**：属性、事件、分群、函数、行为序列；可排序截断人数。
2. **导入**：上传 ID 与已有属性匹配。
3. **结果**：点分析表带下划线的人数保存；自定义 SQL 分析不能这样存。

列表可按运行状态、创建方式、更新方式、计算状态、创建人筛。详情有历史计算结果、可暂停例行任务。画像套件还有血缘、推送通道、特征分群等，超出本次截图范围。

**分析版没有一等公民「SQL 分群」**（SQL 标签在画像里）。数数把 SQL 分群做成和条件分群并列的类型。

神策规则条件可嵌套「已有分群」；截图里数数三种条件未展示分群套分群，手册里分析筛选可以选择已有分群。

## 5. 我们现在有什么

v1 PRD 把用户分群、画像、标签、RFM 放在非目标。仓库里没有分群资产、没有成员表、分析筛选不能选「属于某分群」。

可复用的底座：

- 事件：`clklog_sa.sa_events`（`distinct_id` / `user_key` / `device_id`）
- 画像：`clklog_sa.sa_user_profiles`
- 分析去重口径固定 `if(user_key != '', user_key, distinct_id)`，**不能切换分析主体**（事件分析靠拢数数时明确没做）
- 事件/用户属性筛选、漏斗步序（接近「依次做过」，但不是分群资产）
- 自定义 SQL：只读、有界；可参考 SQL 分群的编辑器，但不能当运营圈人引擎用

没有：成员预计算与刷新、结果分群入口、分群当筛选、分析主体管理、分群列表页。

## 6. 差异（设计输入）

按「没有它，分群不像分群」排序：

1. **预计算成员表 + 刷新**（创建即算；条件/SQL 可日更或手动）。缺这个，分析每次即席圈人会打爆 ClickHouse，也和他们对标产品不一致。
2. **条件分群三种谓词**：做过/没做过、依次/没依次、用户属性。这是运营和增长最常用的入口。
3. **分析筛选「属于 / 不属于分群」**。只建群不能用，等于没有产品。
4. **结果分群**：从事件/漏斗/留存的人数下钻保存快照。创建页可以没有这张卡，但分析表要有入口。
5. **ID 分群**：CSV 对外部名单。对不上的行丢弃。
6. **SQL 分群**：有界只读 SQL，结果一列主体 ID；可复用现有 SQL 防护。神策分析版没有对等物，不是第一期必做。
7. **分析主体**：数数分群的第一列。我们只有一种去重键。第一期可只做预置「用户」= 现有口径，主体管理页后置。
8. **列表元数据**：类型、计算方式、最后计算时间、人数、创建人、备注。列显隐是体验，不是能力。
9. **用户列表 / 下载**：点人数下钻。有界 LIMIT。
10. **标签、运营推送、血缘、实时分群、分群套分群、多时区结算**：对标有、截图没有或弱；不要塞进第一期。标签 / SQL 分群 / 分析主体 / SQL 与看板的后续 PRD：`prd-clklog-analytics-user-segment-followups.md`。

红线约束（写 PRD 时必须写进非目标或验收）：

- 成员表只能落 `clklog_sa`，不改社区版表。
- 圈人 SQL 必须有 `project_name` + 时间/LIMIT/超时。
- SQL 分群走只读账号，禁止 DDL/DML。
- 自定义 SQL 分析 **不要** 做成结果分群入口（神策明确不支持）。
