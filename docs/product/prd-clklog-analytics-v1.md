# PRD：ClkLog 分析平台 v1

> phase: clklog-analytics-v1
> 版本：v1.0（2026-07-28）｜ 上游：`docs/architecture/analytics-extension-plan.md`（调研与总体方案）｜ 下游：`docs/architecture/clklog-analytics-design.md`
> 对标：神策分析（Sensors Analytics）的埋点管理、事件分析、漏斗分析、留存分析、报表。

---

## 1. 背景与目标

ClkLog 社区版仅提供固定预置报表（PV/UV/渠道/地域等），自定义事件属性未入库，无通用分析模型。本 phase 交付一个对标神策的分析平台 v1：补齐全属性数据采集，提供埋点管理 + 四大分析能力 + 自定义报表，供产品/运营/研发自助分析。

**量化目标**：DAU 5 万（约 250 万事件/天）规模下，事件分析 P95 < 3s、漏斗 P95 < 5s、留存 P95 < 8s。

## 2. 阶段目标与范围（门禁要素①）

本 phase 包含总体方案的 P0~P3：

| 范围 | 内容 |
|------|------|
| 数据补齐 | 旁路消费 CKafka → `clklog_sa.sa_events`（含完整自定义属性 JSON）+ `sa_user_profiles` |
| 埋点管理 | 元事件/事件属性/用户属性管理、虚拟事件、Debug 实时数据查询、入库校验报告 |
| 事件分析 | 多指标 × 筛选 × 分组 × 时间粒度 × 时间对比 |
| 漏斗分析 | 按人数漏斗：窗口期、步骤筛选、趋势、模板 |
| 留存分析 | 自定义初始/回访事件，日/周/月粒度，留存表+曲线 |
| 自定义报表 | 看板、卡片（分析书签）、自定义 SQL（只读限额） |

## 3. 用户与角色

| 角色 | 核心诉求 |
|------|---------|
| 埋点研发 | 登记埋点方案、查 Debug 实时数据、验收数据质量 |
| 数据分析师 | 事件/漏斗/留存分析、自定义 SQL、搭建看板 |
| 运营/产品 | 看现成看板、做简单的事件/漏斗查询 |
| 管理员 | 元数据治理（隐藏废弃事件、物化高频属性）、权限 |

## 4. 功能需求

### 4.1 埋点管理

| # | 功能 | 需求描述 | 优先级 |
|---|------|---------|--------|
| M1 | 元事件自动发现 | ingestor 见到新 event 自动登记（状态=待确认），含首见时间、近7天量 | P0 |
| M2 | 元事件管理 | 显示名、描述、负责人、状态（待确认/可见/隐藏）；隐藏事件不出现在分析选择器 | P0 |
| M3 | 事件属性管理 | 自动采样属性 key/类型/示例值；人工可改显示名与数据类型（String/Number/Bool/Datetime/List） | P0 |
| M4 | 用户属性管理 | 同 M3，作用于 user_set 类数据 | P0 |
| M5 | 虚拟事件 | 元事件+筛选条件的组合，可命名后在全部分析模块当事件用 | P1 |
| M6 | Debug 实时查询 | 按 distinct_id/user_key/事件名查最近 100 条原始事件（含 properties 原文） | P0 |
| M7 | 入库校验报告 | 已登记属性 vs 实际上报：类型不符、未登记属性、缺失必填属性 三类清单 | P1 |
| M8 | 属性物化 | 高频属性一键物化为 ClickHouse 列（`p_` 前缀），物化后分析查询走列 | P1 |

### 4.2 事件分析

| # | 功能 | 需求描述 | 优先级 |
|---|------|---------|--------|
| E1 | 指标 | 触发次数、触发用户数、属性聚合（sum/avg/max/min/去重计数/p50/p90/p99）、人均次数 | P0 |
| E2 | 筛选 | 事件属性+用户属性；操作符：=、≠、in、包含、正则、>、≥、<、≤、有值/无值；且/或组合 | P0 |
| E3 | 分组 | 事件属性、用户属性、时间粒度（时/天/周/月）；分组 TopN（默认 20）+「其他」桶 | P0 |
| E4 | 时间 | 任意时间范围；时间对比：上期/去年同期/自定义 | P1 |
| E5 | 图表 | 折线/柱状/数值卡/表格；可切换 | P0 |
| E6 | 保存 | 存为书签（卡片）上看板 | P0 |

### 4.3 漏斗分析

| # | 功能 | 需求描述 | 优先级 |
|---|------|---------|--------|
| F1 | 漏斗定义 | 2~8 步（一期上限 8，神策 64），每步=事件+筛选条件+别名；拖拽排序 | P0 |
| F2 | 窗口期 | 1 分钟~3650 天自定义，默认 7 天 | P0 |
| F3 | 口径 | 按人数：有序、允许穿插、取首次最长转化序列、同用户多次完成仅计 1 次（语义以 §7 为准） | P0 |
| F4 | 指标 | 每步人数、逐级转化率、总转化率、流失人数 | P0 |
| F5 | 趋势 | 按天/周/月粒度看各步人数与转化率趋势 | P1 |
| F6 | 筛选/分组 | 全局筛选（事件属性+用户属性）；单分组查看漏斗 | P1 |
| F7 | 时间区间限制 | 可勾选「限制窗口期在时间区间内」 | P1 |
| F8 | 漏斗模板 | 保存/应用/管理常用漏斗 | P1 |
| F9 | 图表 | 漏斗图 + 明细表格 | P0 |

### 4.4 留存分析

| # | 功能 | 需求描述 | 优先级 |
|---|------|---------|--------|
| R1 | 留存定义 | 自定义初始事件、回访事件（可不同），各带筛选条件 | P0 |
| R2 | 口径 | 两种：首日新用户（is_first_day）/ 时段内触发初始事件的全部用户 | P0 |
| R3 | 粒度 | 日/周/月；N 值可选 D1~D30 自定义（默认 1/2/3/7/14/30） | P0 |
| R4 | 输出 | 留存人数表（cohort×N）+ 留存率曲线（多 cohort 对比） | P0 |
| R5 | 筛选 | 全局事件属性+用户属性筛选 | P1 |

### 4.5 自定义报表

| # | 功能 | 需求描述 | 优先级 |
|---|------|---------|--------|
| B1 | 看板 | 创建/编辑/删除看板；卡片网格布局拖拽 | P0 |
| B2 | 卡片 | 四类来源：事件分析/漏斗/留存/自定义 SQL；存分析 DSL 快照，打开实时重算 | P0 |
| B3 | 全局筛选 | 看板级时间范围、项目切换，下推所有卡片 | P1 |
| B4 | 自定义 SQL | 自由 SELECT 查 `clklog_sa`；只读执行 + 超时/行数限额 + 危险关键字拦截 | P1 |
| B5 | 权限 | 看板所有者/只读分享链接 | P2 |

## 5. 验收标准（门禁要素②）

### 5.1 数据补齐

- [ ] A1：同一时段 `clklog_sa.sa_events` 与 `clklog.log_analysis` 的 track 事件行数一致（误差 < 0.1%，仅允许位点提交间隙差异）
- [ ] A2：上报含自定义属性的事件（如 `{"product_id":"P1","amount":99.5}`），可在 `sa_events` 用 `JSONExtractString(properties,'product_id')='P1'` 查到
- [ ] A3：上报 `user_set` 后，`sa_user_profiles` 可按 distinct_id 查到该属性
- [ ] A4：ingestor 重启后从位点续传，不丢数据（kill 后重启对比行数）

### 5.2 埋点管理

- [ ] B1：新事件上报后 5 分钟内出现在元事件列表（状态=待确认）
- [ ] B2：隐藏事件后，分析模块事件选择器不再出现该事件
- [ ] B3：M6 用指定 distinct_id 上报 3 条事件，可查到原始 JSON 且属性完整
- [ ] B4：虚拟事件「注册且渠道=app_store」在事件分析中可选中且结果 = 元事件加条件的查询结果

### 5.3 事件分析

- [ ] C1：E1 全部指标类型可出数；与手工 SQL 对拍一致
- [ ] C2：且/或混合筛选结果正确；用户属性筛选生效
- [ ] C3：分组 TopN + 其他桶数量 = 未分组总数
- [ ] C4：DAU 5 万等价数据量下 P95 < 3s

### 5.4 漏斗分析（语义对拍，逐条执行）

- [ ] D1：序列 A>X>B>X>C（X 为任意穿插事件）→ 判定全转化
- [ ] D2：序列 A>B>C（漏斗 A>B>C>D）→ 判定 C 步流失
- [ ] D3：序列 A>B1>B2>C → 转化归于 B2（就近归属）
- [ ] D4：序列 A>B1>C>A>B2>C → 取首次最长序列 A>B1>C，仅计 1 次
- [ ] D5：序列 A1>B1>A2>B2（未完成）→ 以靠后的 A2>B2 判定流失步
- [ ] D6：窗口期 1 天，A 与 B 间隔 25h → 不转化；间隔 11h → 转化
- [ ] D7：时间范围只约束第一步；勾选「限制窗口期在时间区间内」后，区间外的后续步骤被截断
- [ ] D8：步骤带属性筛选（如步骤2 支付方式=支付宝）→ 仅计该属性值的转化
- [ ] D9：同一用户窗口期内完成 3 次 → 人数仅计 1
- [ ] D10：无漏斗外筛选时，第 1 步人数 = 事件分析同事件同条件的触发用户数
- [ ] D11：DAU 5 万等价数据量下 P95 < 5s

### 5.5 留存分析

- [ ] E1：构造已知答案的 30 天测试数据，D1/D7/D30 留存人数与留存率和手工 SQL 对拍一致
- [ ] E2：初始事件 ≠ 回访事件（如 注册→下单）出数正确
- [ ] E3：周/月粒度 cohort 正确聚合
- [ ] E4：「首日新用户」与「全部触发用户」两种口径切换结果不同且各自对拍正确
- [ ] E5：P95 < 8s

### 5.6 自定义报表

- [ ] F1：四类卡片可创建、上看板、实时重算出数
- [ ] F2：自定义 SQL 执行 `DROP TABLE` 被拦截；单条 SQL 超时 30s 熔断；返回行数硬上限 10 万
- [ ] F3：看板全局时间筛选下推全部卡片

## 6. 非目标（门禁要素③，本 phase 明确不做）

1. 按次数漏斗、漏斗属性关联（跨步骤同一属性值约束）、转化中位时间 → v2
2. 分组留存、留存的用户属性分组 → v2
3. 用户 ID-Mapping 离线打通（匿名历史数据归并刷数）→ v2+；v1 仅运行时 `if(user_key!='',user_key,distinct_id)` 归并
4. 用户分群、用户画像、标签体系、RFM → 后续 phase（对标 CDP）
5. 分布分析、间隔分析、归因分析、Session 分析、用户路径、热力图 → 后续 phase
6. 埋点方案的需求评审流（结构化 tracking plan 管理）→ v2
7. 定时邮件/企微订阅报表、智能预警 → 后续 phase
8. 多语言、移动端 App → 不考虑
9. 修改 ClkLog 社区版任何功能与表结构 → 永久不做（红线）

## 7. 口径与语义基准

漏斗/留存/事件分析的精确定义以 `docs/architecture/analytics-extension-plan.md` 附录 A（神策官方语义提取）为唯一基准；§5 的 D/E/C 系列验收用例由其推导。任何实现与基准冲突时，以基准为准或在文档显式声明偏差。

## 8. 依赖与约束

- 依赖：CKafka topic `clklog` 消息保留期 ≥ 7 天（P0 上线前需确认，不足则调长）；ClickHouse 磁盘余量 ≥ 200GB。
- 约束：遵守 `AGENTS.md` 红线（旁路扩展、查询有界、密钥不入库）。
- 部署：与现有 Puppet 体系集成，`/sa/` 路径挂在 `管理后台入口`。
