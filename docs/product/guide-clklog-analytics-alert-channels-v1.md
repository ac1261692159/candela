# 配置指南：告警通知通道（多通道）

- `phase: clklog-analytics-alert-channels-v1`
- 适用版本：17238 起（通道平台化配置 + 多联系人 + 保留策略）
- 相关：PRD `prd-clklog-analytics-alert-channels-v1.md`、设计 `clklog-analytics-design-alert-channels-v1.md`、调研 `research-clklog-analytics-alert-channels-v1.md`

开源分发**不预置任何厂商凭证**：默认全部通道不可用，按需配置即可。

## 1. 通道一览与配置位置

| 通道 | 凭证在哪 | 联系人的字段 | 前置条件 / 注意 |
|---|---|---|---|
| 飞书 | 联系人 | Webhook 地址 + 签名密钥（可选） | 群机器人；HTTP 200 也可能带错误码，平台已校验；机器人开了「签名校验」时必须填签名密钥，否则报 **19021** |
| 钉钉 | 联系人 | Webhook 地址 + 加签密钥（可选） | 官方限流 **20 条/分钟**；加签算法：`Base64(HmacSHA256(secret, ts + "\n" + secret))`，ts 毫秒 |
| 企业微信 | 联系人 | Webhook 地址（含 key） | 官方限流 **20 条/分钟**；正文超 2048 字节自动截断 |
| Telegram | 通道配置（Bot Token）+ 联系人（chat_id） | chat_id | 官方限流群 20 条/分钟；大陆需代理，可改 api_base |
| 通用 Webhook | 联系人 | URL + 请求头 + body 模板 | 长尾渠道（PagerDuty/自建系统）用它，零代码接入 |
| 邮件 | 通道配置（SMTP）+ 联系人（邮箱） | 邮箱 | 未配置时回退环境变量 `ALERT_SMTP_*` |
| 短信 | 通道配置（厂商）+ 联系人（手机号，可指定厂商） | 手机号 | 国内签名/模板需控制台报备；AWS SNS 无大陆区域 |
| WhatsApp | 通道配置（Token + 模板）+ 联系人（号码） | 号码（E.164 无 +） | 需 Business 验证 + 模板审核；窗口外只能发模板消息 |

### 1.1 验证状态：「代码层全绿」覆盖到哪里

配置任何通道前先看这张表。**代码层只覆盖「我们这一半」**——请求构造、鉴权、厂商错误码解析、限流与合并、
重试、平台邮件回落、暂停投递；**不覆盖「厂商那一半」**——账号状态、签名/模板报备与审核、沙箱放行、
额度、跨境网络。所以「单测全绿」不等于「这条通道一定能发出去」，两者的边界如下：

| 通道 | 我们这一半（代码） | 厂商那一半（真实账号） | 证据 / 说明 |
|---|---|---|---|
| 邮件（SMTP） | ✅ | ✅ 已实测 | 2026-10-09：163 邮箱经平台邮件通道发到 Gmail 收件箱；测试发信与真实告警各一封 |
| Telegram | ✅ | ✅ 已实测 | 2026-10-09：真实 Bot + chat_id 收到测试消息；含 `chat not found`（未点 START）的排障路径 |
| 飞书（含签名校验机器人） | ✅ | ✅ 已实测 | 2026-09-16 生产实测（见 `acceptance-clklog-analytics-alert-channels-v1.md` §4.1，含 19021 加签修复） |
| 钉钉 / 企微 / 通用 Webhook | ✅ 单测 + 契约 | ⚠️ 无实测记录 | 交付时列为「只能人工确认」（同上验收记录 §5）；webhook 即凭证，出错会在「通知记录」给出厂商错误码 |
| WhatsApp（Cloud API） | ✅ 单测（模板参数、E.164 校验） | ❌ 未验证 | 需 Business 验证 + 模板审核；卡片表头「?」已给前置条件与验证方法 |
| 阿里云短信 / 腾讯云短信 | ✅ 单测（模板参数、错误解析） | ❌ 未验证 | 需开通 + 签名/模板报备审核 |
| AWS SNS / Twilio | ✅ 单测 | ❌ 未验证 | 需沙箱放行 / 购号；SNS 无 cn-* 区域 |

**结论（2026-10-09 与用户确认）**：只靠代码层**不能**保证未验证通道端到端可用。可行的替代是
「把验证成本压到一次点击」——填好凭证后点「发送测试」：成功即通；失败会带回**厂商原始错误码**，
按码去厂商文档定位即可，不需要改代码、不需要发版。这条路径对 7 个凭证级通道都适用。

## 2. 配置步骤（以邮件为例）

1. 运维 → 监控告警 → **通道配置** → 展开「邮件（SMTP）」→ 填 host/port/用户名/密码/发件人 → **保存**（密钥只写不读）。
2. 填「测试收件邮箱」→ **发送测试**：先做 SMTP 连通性校验，再实发一封；失败会显示厂商原始错误。
3. 运维 → 监控告警 → **联系人** → 通道选「邮件」→ 填邮箱 → 添加（默认启用）。
4. 规则绑联系人：新建/编辑规则时「告警联系人」可**多选**（一条规则发到多个渠道）。不绑定时，
   告警发给**全部启用中的联系人**；联系人可在列表里用「启用」开关随时停用（停用即不投递）。
   联系人建好后发现填错，用操作列「编辑」改（地址与密钥在列表里是脱敏的，编辑框留空 = 不修改）。

> 短信与 Telegram/WhatsApp 同理：先在「通道配置」保存凭证并测试，再到「联系人」建接收人。
> 保存凭证需要平台设置环境变量 `ALERT_CONFIG_KEY`（32 字节 base64，`openssl rand -base64 32` 生成）；平台会加密存储。

### 2.2 Telegram 逐步配置（与表头「?」的帮助原文一致）

Telegram 是「漏一步就报错、而报错看不出所以然」的典型，因此它的卡片表头右侧有一个 **「?」**，
点开就是这个通道的四步配置方法；其余通道不显示「?」（说明仍在展开区里）。

1. 在 Telegram 里搜 `@BotFather` → 发送 `/newbot` → 按提示设显示名与用户名（**用户名必须以 `bot` 结尾**）
   → 把它返回的 Token 填到「Bot Token」并保存。
2. **用你自己的 Telegram 打开这个机器人，点「START」（或随便发一句话）**。机器人不能主动发起会话——
   漏了这步，发送测试会返回 `chat not found`（这是 Telegram 的原文，不是平台报错）。
3. 联系人的 `chat_id` 填 `@userinfobot` 回给你的数字 ID（私聊就是你的用户 ID）。
   要发到群：先把机器人拉进群，再到 BotFather 用 `/setprivacy` 关掉隐私模式，否则它收不到群消息。
4. 服务器出海受限时，把「API 地址」改成自建 Bot API 服务地址；留空即官方 `api.telegram.org`。

> 2026-10-09 生产实测：按上述四步在 `smtp` 与 `telegram` 两条通道各收到一条测试消息；
> 漏做第 2 步时的原始返回为 `telegram_http_400({"error_code":400,"description":"Bad Request: chat not found"})`。

## 2.1 通知记录怎么看（多联系人）

一条规则绑定多个联系人时，同一事件会在「通知记录」里**按投递目标分行**显示（列「联系人」），
失败行的「错误」列是厂商原始错误码——所以「一条通道成功、另一条失败」能一眼看出是哪条。

## 3. 限流与合并（官方硬约束）

钉钉/企业微信/Telegram 官方限流均为 **20 条/分钟**（钉钉超限还会被限流 10 分钟）。平台在通道层做了：

- **令牌桶 + 发送间隔**：按通道限流值自动排队，不会打到厂商限流；
- **积压合并**：同一通道一轮积压 ≥ 3 条时合并为一条「告警汇总」摘要（列前 5 条规则名 + 剩余数量）；
- 失败重试 3 次（退避 1s/2s），最终失败会在「通知记录」里保留**厂商原始错误码**。

## 4. 手动测试清单

| # | 场景 | 期望 |
|---|---|---|
| 1 | 未配置任何凭证时打开「通道配置」 | 各通道显示「未启用」，联系人里对应通道置灰并给出原因 |
| 2 | 配置 SMTP → 发送测试 | 收到测试邮件；错误密码时提示认证失败（原始错误码） |
| 3 | 建飞书联系人 → 规则触发 | 收到告警；内容与「通知模板 → 群聊」一致 |
| 4 | 建钉钉联系人（不填密钥） | 机器人若设为「加签」则投递失败并显示钉钉错误码；填上密钥后成功 |
| 5 | 建企业微信联系人 → 触发 | 群里收到消息（2026-10-10 起通道集为 8 个：飞书 / 钉钉 / 企业微信 / Telegram / 通用 Webhook / 邮件 / 短信 / WhatsApp） |
| 6 | 建 Telegram 联系人（chat_id） | 收到消息（大陆需代理出口） |
| 7 | 建通用 Webhook 联系人（自定义 body 模板） | 目标服务收到自定义 JSON，`{{.text}}`/`{{.text_json}}` 被替换 |
| 8 | 短信（厂商已报备模板） | 收到一行摘要短信 |
| 9 | 一次性让多条规则触发（≥3 条） | 通道只收到一条「告警汇总」，通知记录里各规则均为成功 |
| 10 | 通知模板改「群聊」文案 → 触发 | 收到的内容使用新模板（左侧编辑、右侧预览实时刷新） |
| 11 | 联系人列表关掉某联系人的「启用」开关 → 触发规则 | 该联系人不收；把规则绑定到这个联系人时同样不投递（回退到其它启用联系人） |
| 14 | 飞书机器人开了「签名校验」→ 联系人里填签名密钥 → 发送测试 | 收到消息；通知记录里该行显示联系人名（含密钥的机器人也能投递） |
| 12 | 规则绑定两个不同通道的联系人（如飞书 + 邮件）→ 触发 | 两个渠道都收到，通知记录里同一事件两行 |
| 13 | 概览 → 数据保留策略：把「通知记录」改成 30 天并保存 | 策略立即生效（下次清理按新值），变更记录里出现一条「修改保留策略」 |

## 5. 故障排查

| 现象 | 排查 |
|---|---|
| 联系人里通道置灰 | 「通道配置」里该通道未启用/未保存成功 |
| 投递失败 | 「通知记录」看 error（形如 `dingtalk_errcode_310000`、`telegram_error_400`，即厂商原始返回） |
| 长时间没收到 | 是否被同通道限流排队（20 条/分钟）；是否为屏蔽期；是否规则未命中 |
| Telegram/WhatsApp 超时 | 出口网络（大陆需代理）；Telegram 可在配置里改 api_base 指向自建 Bot API |
| 保存凭证报错 | 未设置 `ALERT_CONFIG_KEY`（主密钥），或该通道必填字段缺失 |
