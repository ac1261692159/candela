# 数据管理模块设计（clklog-analytics-data-management-v1）

状态：设计评审中 · 作者：CodeBuddy · 日期：2026-09-07
上游：运维面板 PRD（prd-clklog-analytics-ops-console-v1）、数据治理对拍设计（clklog-analytics-design-data-governance.md §4）、HANDOVER §11.2

---

## 1. 背景与问题（2026-09-07 实测）

| 事实 | 来源 | 影响 |
|---|---|---|
| 数据盘已用 50% 且增长快 | 用户报告 + 运维面板磁盘采样 | 无清理手段，预计数月内用尽 |
| `clklog_sa.sa_events` 亿级行（单机） | system.parts | 排序键 event 打头，stat_date 过滤只有月分区剪枝，任何按时间查询都是亿行级 |
| CH 容器 memcg 12GiB，内存常年贴顶 | 19:08 OOM 记录 | 重查询=全局事故（对拍两次打挂 CH，见 HANDOVER 复盘） |
| `log_analysis`（社区版）无 project 隔离、无 TTL | 表结构 | 与 sa_events 双份存储，占盘主力 |
| `log_analysis` 存在未来时间戳数据（09-08/09-20） | 对拍发现 | 设备时钟错乱，污染按日统计 |
| sa_events 比 log_analysis 系统性多 1.2-1.3% | 对拍发现 | 写入路径差异，成因未明 |
| log_time 不在 sa_events 排序键前缀 | 表 DDL | 「最近 N 条」类查询必须带时间下界，否则全表扫 |

**结论**：数据管理不是一个「删除按钮」，是在**单机小内存 CH** 约束下的数据生命周期治理。

## 2. 定位与权限

- 菜单：**运维面板 → 数据管理**（与 慢SQL/服务器状态/监控告警 同级），仅 admin 超管可见（复用 ops 面板的两层拦截：菜单隐藏 + `/ops/*` 服务端鉴权）。
- 服务端两道闸的**具体落点**（2026-09-18 修正，此前数据管理误挂 `meta.view`）：第一道 `@RequirePermission('ops.runtime.access')`（项目管理员不持有该码），第二道 handler 内 `assertOpsAdmin` 身份兜底（`platform_role === 'super_admin'`）。新增 `/ops/*` 接口必须同时具备两道。
- 原则沿用运维面板：**查询/预演纯只读；一切写动作（清理）单独走「动作类」流程：预演 → 二次确认（输入表名）→ 执行 → 审计留痕**。

## 3. 功能设计

### 3.1 存储概览（只读，首屏）

- 各库各表：行数、压缩后/原始字节、分区数、最近写入时间（`system.parts` 按 active 聚合；复用 server-status 现成的 system 查询路径）。
- **按月存储趋势图**（复用趋势图组件）：`system.parts` 按 partition 聚合的行数/字节历史——注意 `system.parts` 只有当前快照，**趋势需自建采样**：复用 `metric-sampler.service` 模式，每 5 分钟采样各表 `sum(rows)/sum(bytes)` 落 MySQL 表 `ops_metric_sample`（与磁盘采样同表，metric_key 扩展 `table:{db}.{tbl}:rows|bytes`）。留存 ≥90 天。
- 增长率与「预计用尽日期」：与磁盘预测同算法（线性回归外推，复用 trend-forecast 纯函数）。

### 3.2 数据清理（动作类，核心）

**3.2.1 策略盘点（只读）**：列出各表当前 TTL、分区粒度、可清理候选（超过 N 天的分区）。

**3.2.2 清理手段分级**（按安全性与代价排序）：

| 手段 | 适用 | 代价 | 风险 |
|---|---|---|---|
| **TTL 设置**（`ALTER TABLE ... MODIFY TTL`） | log_analysis / sa_events 等日志类表的常规生命周期 | 一次性 DDL，后台渐进生效 | 低（可随时 MODIFY 回退）；**首选** |
| **DROP PARTITION**（按月） | 大批量历史数据下线 | 秒级元数据操作 | 中（不可恢复，需预演+确认）；次选 |
| **ALTER DELETE**（条件删） | 定点清脏数据（如未来时间戳行） | mutation，后台重写分区，占 IO | 高（长 mutation 拖垮磁盘 IO）；仅限小范围定点，须 `mutations_sync=0` + 监控 |

**3.2.3 清理预演（dry-run，只读）**：选定 表+范围 → 返回将影响的分区清单、行数、字节数、释放磁盘预估。预演查询带 4GB 内存上限 + 2 线程（对拍同款护栏）。

**3.2.4 执行流**：预演结果页 → 输入表名二次确认 → 执行 → 动作写入审计表 `ops_action_log`（who/when/what/dry_run_snapshot）→ 清理后自动刷新存储概览。

**3.2.5 V1 内置推荐策略**（预填、可改）：
- `log_analysis`：TTL `log_time + 180 DAY`（与社区版对齐，先盘点用户意图）
- `clklog_sa.sa_events`：保留策略待定（旁路分析库是分析主数据，V1 **只盘点不默认清理**）
- `system.query_log` / `trace_log` 等 CH 系统表：TTL 30 天（对拍慢 SQL 依赖 ~3 天留存，30 天绰绰有余）

### 3.3 对拍集成（迁移还是聚合？——**聚合**）

**决策：数据质量页（对拍/Debug）保留在「元数据」菜单原位，数据管理不做页面迁移，只做入口与能力复用。** 理由：
- 对拍是「数据正确性」问题，数据管理是「数据生命周期」问题，语义不同；
- 迁移会破坏现有书签与用户习惯；
- 数据管理需要的是对拍的**结论**（dup 率、偏差率）作为清理决策输入，聚合展示即可。

实现：数据管理首页加「数据健康」卡片，读对拍最近一次结果（reconcile 缓存化——当前对拍 59s 不适合每次进页面都跑；新增 `ops_reconcile_snapshot` 表，对拍完成后落快照，页面读快照+显示「上次对拍时间」+手动触发按钮）。

### 3.4 慢查询

运维面板慢 SQL 已覆盖（system.query_log，~3 天留存）。数据管理不重复建设，仅在清理预演页提示「清理 mutation 会与慢查询共享 IO 预算」。

## 4. 非功能约束（从对拍事故直接推导）

1. **一切对 sa_events/log_analysis 的扫描查询必须带**：时间下界、`max_memory_usage=4GB`、`max_threads=2`、600s 上限（单机 12GiB 教训，HANDOVER §11.2）。
2. DROP PARTITION / ALTER DELETE 走 **write 账号 + 审计**；查询走只读路径。
3. 清理动作前自动 `SHOW CREATE TABLE` + 分区清单快照落审计表（可追溯）。
4. mutation 执行后轮询 `system.mutations` 展示进度，未完成前禁止发起新清理（IO 保护）。
5. 未来时间戳脏数据：V1 先出**检测视图**（每日行数 vs 系统日期），清理 ALTER DELETE 在数据管理 V1.1（需先确认时钟错乱设备范围）。

## 5. 页面结构（运维面板 → 数据管理）

```
数据管理
├─ 存储概览（表清单 + 按月趋势 + 预计用尽）
├─ 数据健康（对拍快照摘要 + Debug/数据质量入口链接）
├─ 清理策略（TTL 盘点 + 推荐）
└─ 清理执行（预演 → 确认 → 执行 → 审计记录）
```
