## 3. 验收抓出的两个缺陷（都已修 + 复验）

1. **字段名不一致（17659）**：前端发 `rows`，后端 DTO（`forbidNonWhitelisted`）只认 `limit` → 查询直接 400。
   修前端为 `limit`（与 Debug 查询同名字段）。复验：同一查询返回 201。
2. **跨 kind 串味（17660）**：记录表泛化出 `user_timeline` 后，`DebugArchiveService.claimNextPending()` 只按 status 找 pending，
   **Debug runner 把时间线的任务抢走**、用 debug 规格执行 → 记录 `failed(query_failed)`。
   修：Debug 侧所有按记录表的读写（认领/回收/列表/详情/删除/去重）限定 `kind='debug'`；单测补三条断言钉住。
   复验：把该记录重置为 pending → `TimelineJobRunner` 正确认领并在 8.9s 内完成（命中 2445、落档 500 行）。

> 教训：**同一张表承载多种 kind 时，认领/回收这类「按状态扫描」的查询必须同时限定 kind** ——
> 否则两个 runner 会互相抢任务，而且症状是「A 的任务被 B 用错误规格跑失败」，日志里才有线索。

### 8.2 第一次验收：**属性路径直接失败**（真实缺陷，非测试写法问题）

| 查询 | 结果 |
|---|---|
| A 按用户标识 `样例标识`（13:00~15:00） | 后台 **39.1s** 完成：命中 **1495**、事件种类 **101**、落档 500 行 |
| B 按用户属性 `massid=样例业务号`（同区间） | 后台运行后 **failed（`query_failed`）**，连续两次 |

服务日志给出的原始报错（不是语法错，是引擎的**预估时长保护**）：

```
ClickHouse 查询失败: … FROM clklog_sa.sa_events
  LEFT JOIN (SELECT distinct_id AS uid, properties FROM clklog_sa.sa_user_profiles FINAL
             WHERE project_name = {project: String}) AS up_1 ON sa_events.distinct_id = up_1.uid
  WHERE project_name = {project: String}
    AND JSONExtractString(up_1.properties, {id_key: String}) = {value: String} …
Error: Estimated query execution time (180.26561317345764 seconds) is too long.
       Maximum: 120. Estimated rows to process: 95504511: While executing MergeTreeThread.
```

**根因**：把「用户属性等值」作为**事件表**的过滤条件（哪怕以 JOIN 形式），事实表就失去了全部剪枝能力。
ClickHouse 按 `stat_date` 区间（两端各留 2 天）整段预估 → **千万级行 / 180 秒** > 120 秒上限 →
后台任务直接失败。而同区间的真实数据只有 1495 条。注意 A（主体口径）能过是因为主体表达式之外
没有额外 JOIN，成本量级完全不同。

### 8.3 修复：两段式解析（见设计 §11.2 红线）

1. 先在**画像表**（十万行级）解析 `massid = 样例业务号 → distinct_id = 样例标识`；
2. 再用**与 `id_kind=subject` 完全相同**的主体表达式限定事件（单标识 `=`、多标识 `IN`），**不引入任何 JOIN**；
3. 解析不到 → 400 `timeline.userNotFound`（带属性键与值的本地化提示），而不是静默返回空表；
4. `profile` 同样支持按属性定位，并回报 `resolved` / `matched_users`，页面显示「**已解析为用户标识 样例标识**」；
5. `filter_scope=user` 的行级筛选改走同一解析路径（筛不到 → 条件 `1 = 0`，空结果而非报错）。

单测钉住 SQL 形状：属性路径的事件 SQL **不含 `JOIN`、不含 `{id_key`**，且形态与主体口径同形
（`timeline.service.spec.ts`：单标识 `= {ident}`、多标识 `IN {idents}`、解析为空 → 400、用户属性筛选 → 恒假分支）。

### 8.7 浏览器实测抓出的第二个缺陷（版本 17671）

复验英文标签时**误操作反而暴露了一个真实缺口**：把标识类型切到「用户属性」、填入属性值、
但**没有选属性键**就点查询时，请求按标识口径静默执行 → 返回空结果，页面显示「该用户在所选区间内没有上报事件」。

这是最糟的失败模式：分析工具给出**看起来正常但错误的结论**。修两处：

| 层 | 处置 |
|---|---|
| 服务端 | `id_kind` 为 `user_property`/`event_property` 而缺 `id_key` → **400 `timeline.idKeyRequired`**（带 `{kind}` 插值，13 语言齐备）；不再退回标识口径 |
| 前端 | 未选属性键时「查询」按钮置灰（与「未填标识」同一套约束） |

单测：`normalize` 两种属性口径缺键均抛 400、补上键后正常（timeline 36 用例）。
门禁：i18n 13×16=**3879** 键；扫描棘轮持平；后端/前端构建通过；arch_ratchet passed。

**17671 复验（浏览器真实点击）**：

| 检查项 | 实测 | 结论 |
