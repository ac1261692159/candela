# 结论记录：`sa_events` projection（机制已验证，因磁盘容量暂不上线）

> phase: `clklog-analytics-sa-events-projection-v1`
> 日期：2026-10-08
> PRD：`docs/product/prd-clklog-analytics-sa-events-projection-v1.md`
> 实现方案与全部实测数据：`docs/architecture/clklog-analytics-design-sa-events-projection-v1.md`

## 1. 一句话结论

projection **确实能把设备/账号维度压到秒级以下**（演练：设备读行数 19×、耗时 ~10×；账号加第二份投影后 0.02s），
但**存储成本在当前磁盘容量下装不下**（基础表按 18 个月 TTL 的稳态已占满磁盘约 89%，单份投影 +1.0TB、双份 +2.0TB），
因此**不上线**；把「异步查询」（零存储）作为下一候选，保留期与扩盘作为需要产品/运维决策的两条路线。

## 2. 验证了什么（演练，staging）

| 项 | 结果 | 判据对照（PRD） |
|---|---|---|
| 设备维度查询 | 读行数 618,470 → 32,213（19×），1.4s → 0.11–0.20s | PJ-1 ✅（≥10×） |
| 账号维度查询 | 需**第二份**投影才生效；加后 0.019–0.027s | P2 ✅（如实归档） |
| 存储增量 | 单份 ≈ 基础数据 45%–90%；双份 0.9×–1.8× | PJ-2 ✅（已量化） |
| 写入开销 | 单份 +17%、双份 +43%（同切片交替插入实测） | PJ-2 ✅（阈值 ≤50% 内） |
| 幂等 | `ADD PROJECTION IF NOT EXISTS` 重复执行无副作用 | PJ-4 ✅ |
| 自查方式 | `system.projection_parts` / `system.parts.projections`（23.2 **无** `system.projections`） | PJ-4 ✅ |
| 物化 | 327 万行 / 48 秒 | — |
| 回滚 | `DROP PROJECTION`（机制同跳数索引，未在生产验证——因为没上线） | PJ-5 ⚠️ 仅演练层面 |

**结果一致性**：全部探针结果逐值一致（设备 2,445 行命中、返回 20 行、首行 `2026/10/07 13:04:28 base_ui_open_trigger`）。

## 3. 为什么不上线：容量账（硬约束）

| 事实 | 数值 |
|---|---|
| `/data` 可用 | 2.3T（总 2.9T，已用 543G） |
| `sa_events` 现占 / 日增 | 172 GiB / **4.04 GiB/天** |
| 18 个月 TTL 稳态 | ≈ **2.21 TB**；叠加社区库 47.6G 与系统占用后 ≈ 2.58T / 2.9T（余量 ~0.3TB） |
| 投影所需 | 单份 +1.0TB、双份 +2.0TB → **装不下** |

## 4. 过程中的两次方法论纠错（记录在案）

1. **切片不能切掉访问模式**：第一版切片限定 4 个事件，`distinct_id` 的目标 granule 数被低估一个量级
   （排序键首列是 event）→ 本次切片改成「全事件 + 2 小时」并**先核对设备在该切片内有 2445 行**再比较。
2. **不要用空查询下结论**：切片第一次取「今天 09:33–12:33」，而被验证设备最后上报在昨天，
   两个对象都返回 0 行、耗时 0.1s —— 差点把「空查询很快」当成投影的收益。**核验方法本身要先验**（这条已是第二次踩）。

## 6. 下一步（按建议顺序）

1. **重查询异步化**（零存储，与已有留档功能契合）：>N 秒的查询转后台，结果落档后回看；
2. **保留期决策**（产品）：`sa_events` 18 个月 → 6/12 个月，可让投影变得可行；
3. **扩盘**（运维/预算）：+1–2TB 即可让双投影上线，设备/账号 7 天查询进 0.1–0.5s；
4. 窄投影 + 两步查询：工程量最大，收益不如扩盘，列为备选。
