## 2. 线上实测（生产，卡片 DAU-DNU-DOU）

### 2.1 混单位被点名到轴

用 Harness 的写入口提交 `units={DNU: percent_0_100}`、`metric_axis={}`（全部左轴）：

- 提案回执：`{"status":"applied","applied_revision":31}`
- 页面提示（实测原文）：**「同一根轴（左轴）上的指标单位不一致：DAU、DNU、DOU」**
- 图照常渲染（`canvas` 在）——手动配置不阻断，与既有「单位改完立刻生效」一致

改动前这句是「指标单位不一致，不能放在同一数值轴」：既不说哪根轴、也不说哪些指标，而且在双轴语境下这句话本身就是错的。

### 2.2 一键拆轴

打开结果设置面板（实测拿到）：

- 出现按钮「按单位拆轴」与说明「左轴上的指标单位不一致，可把不同单位的指标分到左右两轴」
- 点一下之后回读配置：`metric_axis = {"DAU":"left","DOU":"left","DNU":"right"}`
  - **只搬动了 DNU 一个指标**（少搬动规则生效；若只按「大组留左轴」会把 DOU 也搬走，等于多动一次）
  - 左轴单位集合 `['number']`、右轴 `['percent_0_100']` —— 两根轴各自干净
- 提示消失
- 两轴刻度各按自己的量纲渲染：左轴 `7,000–1.05万`（纯数字），右轴 `1,200%–2,200%`

### 2.3 Harness 侧同步（SC-6）

`GET /tools/query/capabilities` 线上返回：

```
sql_chart.units  = [number, percent_0_100, ratio_0_1, currency, currency_cny, currency_usd, duration_sec, duration_ms, bytes, bytes_iec]
event_chart.units= 同上
sql_chart.notes / event_chart.notes 含「同一根轴」规则 = true，含 ratio_0_1 换算说明 = true
```

改动前模型只知道有 `options.units` 这个名字、不知道合法值（猜错直接 400 `report.chart.unitInvalid`），也不知道同轴必须同单位。**写能力本身验证过**：§2.1 那份 `units + metric_axis` 一次提交即生效——模型可以在一次提案里把混单位状态改成合法状态。

### 2.4 真实模型实测（本 phase 补跑，已通过）

前几轮验收里「浏览器驱动真实模型」一直没跑通（顶层助手视图停在只读预览态）。这一轮找到了原因并跑通：
发送按钮此前用坐标点击/Playwright 定位都送不进事件，**改用「页面内对可见元素派发 click」后正常提交**
（页面上面板控件存在隐藏副本，坐标会打到隐藏节点——与本轮一键拆轴遇到的是同一个坑）。

两轮对话（同一个会话，模型 DeepSeek V4 Flash）：

**第一轮**（起始状态：DNU 被设成 `percent_0_100` 但它是计数，且三个指标同在左轴）

模型自己 `clklog_page_read` → 推理出「DNU 是计数，标成 percent 会显示成 1261%，这是错的」→ 调
`clklog_get_analysis_capabilities`核单位词表 → 一次 `clklog_propose_sql_chart` 把三个指标单位改回 `number`
→ 再 `clklog_page_read` 回读确认。**它没有机械地拆轴，而是判定了根因是单位挂错**——这在一个「单位本身错」
的场景里是更正确的修法。

**第二轮**（换成两种单位都正确的场景：`DAU` 计数 + `新增占比` 百分比同轴）

模型原话：

> 结论：有问题，已改好。这次是双轴缺失（量纲+量级混轴），已一次修正。
> 问题：结果集换成 DAU（人数，8267~10128）和 新增占比（百分比，15.19~21.79）后，两列仍共用一个 Y 轴。
> 占比线会被 8000+ 量级的 DAU 压在底部贴地平线，波动完全看不出来。
> 修正内容（`clklog_propose_sql_chart` 已自动写入，applied_revision 33）：`metric_axis = {"新增占比":"right"}`，并补上 `units.DAU = number`
> 单位选得对，别改：`percent_0_100` 不做换算，而 SQL 算出来的就是 15.25 这种 0–100 数值，配它是对的。
> 若误换成 `ratio_0_1`（渲染时 ×100）就会显示成 1525%，那是反向错误。

回读页面确认：`metric_axis={"新增占比":"right"}`、`units={"DAU":"number","新增占比":"percent_0_100"}`；
图渲染为左轴 `8,400–1.01万`（纯数字）、右轴 `15%–22%`（百分比）；混单位提示不再出现。

这一轮同时验证了三件事：模型**能读到编排**、**能自己诊断出轴/单位问题**、**能在一次提案里同时改 units 与 metric_axis**
（`ratio_0_1` 与 `percent_0_100` 的换算差异说明也确实被它用上了，正是 §2.3 里补进 capability 的那句）。

## 4. 本次改动里的两个判断（记录理由）

1. **压测的取舍：警告而不阻断。** 同轴混单位时页面照画，只是把位置说清并给出路。改成阻断会让使用者手上正在看的图直接消失，代价大于收益；而「自动模式下它不是 error」这一点已经由按轴判定修掉了（跨轴不同单位不再报）。
2. **少搬动优先。** 拆轴规则最初写的是「占比最大的组留左轴」，评审时发现真实场景会翻车：人均(数值,左)、用户数(数值,右)、总量(百分比,左) 会被拆成「右轴＝数值＋百分比」，仍然混。改成比较两种朝向、取搬动更少的一种后，该配置只搬一个指标即可让两根轴各自干净。用例固定了这个场景。
